# The kh-harness contract

Contract number: 1

This document is for the author of another Claude Code plugin that works
inside a repository where kh-harness is installed. It lists everything
kh-harness promises such a plugin: five formats and interfaces, each
described here exactly. A promised format, path, shape, bound or fixed
text changes only with a new contract number. Anything this document does
not state is not promised (see [What is not promised](#what-is-not-promised)).

Each promise is held by a fixture: the files in
`scripts/lib/fixtures/contract-1/` of the kh-harness repository, each shown
below exactly as it is, and the tests named `contract 1: …` in
`scripts/lib/contract.test.mjs`. A change to a promised format fails one of
those tests.

The five promises:

1. [The contract file](#the-contract-file), `.claude/kh-harness/contract.json`.
2. [The rules registry](#the-rules-registry), `docs/harness/RULES.md`.
3. [The manifest](#the-manifest), `.claude/kh-harness.manifest.json`.
4. [The `PreToolUse` extension point](#the-pretooluse-extension-point), `.claude/kh-harness/extensions.json`.
5. [Appending to the session log](#appending-to-the-session-log), `recordExternalEvent`.

All paths are relative to the repository root, with `/` as the separator.
"The kit" means kh-harness.

## The contract file

`.claude/kh-harness/contract.json` says which contract the install in the
repository honours. It is read-only to every other plugin.

- No file means the install is older than the contract, or kh-harness is
  not installed. Treat it as no contract.
- `apply --yes` writes it last in its run, and only when every file it
  speaks for (its `files` key) is on disk holding exactly what this kit
  installs there. While one of them is edited, not recorded in the
  manifest, or deleted, `apply` does not write the contract file.
- `apply --yes` rewrites an existing contract file only when the manifest
  records it as unchanged since kh-harness wrote it, the text this kit
  writes is different (a kit update changes the listed hashes), and every
  listed file holds this kit's bytes once the run has updated them. In
  every other case it leaves the file as it is: an edited contract file, or
  one beside a listed file that is edited, unrecorded or deleted, is
  neither rewritten nor removed, so it can say contract 1 beside files it
  does not describe. A plugin must therefore check the hashes itself (next
  section).
- `uninstall --yes` removes it before any other file. An edited copy is
  kept by `uninstall`.

The file is a JSON object:

| Key | Value |
|---|---|
| `contract` | the contract number, an integer of 1 or more |
| `generatedBy` | the kit's stamp: `Generated by kh-harness <version> (…)`, then a sentence telling a person not to edit it |
| `files` | an object mapping each installed file the number speaks for to the SHA-256 of that file, as lower-case hex, computed as [the hashing rule](#the-hashing-rule) says |

Other keys may appear. kh-harness writes the file as
`JSON.stringify(value, null, 2)` followed by one newline, with LF line
endings. As kh-harness 0.2.0 writes it:

`files` lists the `PreToolUse` entry script,
`.claude/scripts/dispatch-pre-tool.mjs`, and every installed file it loads.
The list itself is what contract 1 speaks for: read it from the file and
do not assume a fixed set. The hashes change with every kit version.

The number speaks for these files only: what they do when they run. It
does not say that anything runs them. The owner can remove a hook
registration at any time.

### The hashing rule

The SHA-256 of a file's bytes after each two-byte sequence CR LF (`0x0D
0x0A`) is replaced by LF (`0x0A`), in one pass over the bytes. A CR that is
not followed by LF is kept. No other byte changes, and no text decoding is
involved. A checkout that turned LF into CRLF therefore hashes the same.

The same rule is used for `files` in the contract file and for an
extension's `sha256` (below).

### How kh-harness itself reads it

For people, kh-harness's `detect` reads the file less strictly than a
plugin must (next section), and what it reports is not promised: a link at the file, at `.claude/kh-harness`, or at a `.claude`
through which the file is reached is no contract number; it reads at most
65,536 bytes; the file must be a JSON object whose `contract` is a safe
integer of 1 or more. A `.claude` that is a link through which no contract
file is reached counts as no file. `P5.contract` is `declared` only when the
file is byte for byte what this kit writes (line endings aside), every file
it speaks for is what this kit installs, and the manifest records it. This
kit honours contract 1 only.

A UTF-8 byte order mark at the start makes the file not JSON. JSON with a
key repeated keeps the last value when parsed, so a file with a repeated
key must be refused by a reader; the check below does that.

## What a plugin must check before relying on contract 1

Before a plugin installs anything that depends on kh-harness, and again
before each use, it checks the install. Do all of the following.

1. **Read the contract file safely.**
   - `.claude`, `.claude/kh-harness` and `.claude/scripts` must each be a
     directory and not a link, and `.claude/kh-harness/contract.json` a
     regular file and not a link. A link at any of them means no contract:
     refuse to install. The repository root itself may be reached through a
     link.
   - Read the file through one descriptor opened so that a link at its last
     component is refused (`O_NOFOLLOW` where the platform has it; also
     `lstat` it first, since win32 has no `O_NOFOLLOW`), then `fstat` the
     descriptor: it must be a regular file. Read at most 65,536 bytes.
   - Parse it as UTF-8 JSON. It must be an object; re-serialised as
     `JSON.stringify(value, null, 2)` plus a newline it must equal the
     file's text with CRLF made LF (this refuses a repeated key and a file
     kh-harness did not write); and `contract` must be an integer this
     plugin supports. For a plugin written against this document: `1`.
2. **Check every hash in `files`. This step is mandatory**: it is the only
   check that the installed scripts are the ones contract 1 describes (see
   [when the kit's own files cannot run the extensions](#when-the-kits-own-files-cannot-run-the-extensions)).
   - `files` must be an object listing `.claude/scripts/dispatch-pre-tool.mjs`.
     A plugin that calls `recordExternalEvent` also requires
     `.claude/scripts/harness-log.mjs`.
   - Every key must match `/^\.claude\/scripts\/[A-Za-z0-9._-]+\.mjs$/`.
   - Each listed file must be a regular file and not a link, of at most
     4 MiB (4,194,304 bytes), read as in step 1, whose hash by
     [the hashing rule](#the-hashing-rule) equals the recorded value.
   - If any key or file fails, the install does not honour the number,
     whatever the number says. Do this before importing any of those files:
     importing one runs it.
3. **Check the `PreToolUse` registration.** Contract 1 does not cover it.
   - `.claude/settings.json` must hold, under `hooks.PreToolUse`, an element
     with no key but `matcher` and `hooks`, whose `matcher` is absent, `""`
     or `"*"`, and whose `hooks` array holds a hook object with **exactly**
     the keys `type`, `command` and `args`, equal to what `apply` writes:
     `{ "type": "command", "command": "node", "args": ["${CLAUDE_PROJECT_DIR}/.claude/scripts/dispatch-pre-tool.mjs"] }`.
   - Claude Code's rule for the matcher: `"*"`, `""` or no matcher fires on
     every occurrence of the event; a matcher of letters, digits, `_`, `-`,
     spaces, `,` and `|` is a list of exact tool names; any other character
     makes it an unanchored regular expression. So any other matcher runs
     the extensions only on some calls.
   - Any other key on the hook object can stop it blocking, or running, on
     some call: `async: true` runs it in the background without blocking,
     `timeout` cancels it sooner, `if` runs it only on matching calls,
     `onFailure` changes what a failure does. With any of them, or a
     narrower matcher, a plugin must not treat its gates as holding for
     every tool call.
   - Neither `.claude/settings.json` nor `.claude/settings.local.json` may
     set `"disableAllHooks": true`; a `settings.local.json` that is there
     must be readable JSON. A registration only in `settings.local.json` is
     not the one `apply` writes and does not count.
4. **Check the plugin's own extension.** Steps 1 to 3 pass with no
   extensions file at all.
   - `.claude/kh-harness/extensions.json` must be a regular file and not a
     link, of at most 65,536 bytes, that kh-harness reads as an extensions
     file by every rule of [the extensions file](#the-extensions-file);
     a file that breaks one blocks every tool call.
   - It must list the plugin's entry exactly: the same `id`, `version`,
     `module`, `sha256` and `onFailure` the plugin wrote.
   - The module must be a regular file under the repository's real
     `.claude/` and outside its real `.claude/scripts/`, of at most
     1,048,576 bytes, whose bytes hash to that `sha256` by the hashing rule.
   - A gate that must hold needs `onFailure: "block"`. With `"allow"`, a
     module that is missing or differs turns the gate off, and only the
     person is told, once per session.

`detect` is a diagnostic for people, not part of the contract: its states
and its output may change without a new contract number, and it reports
`P5.extensions` and `P5.contract` as `declared` for a registration under a
narrower matcher or with `"async": true`. A plugin verifies by the steps
above, performed itself.

What the checks cannot show:

- the user-level settings (`~/.claude/settings.json`), managed policy
  settings and a `--settings` argument, which can set `disableAllHooks`;
  a plugin cannot read them all, and a project setting does not override
  a `--settings` argument or a managed one;
- that the session in progress loaded the settings as they are now on
  disk.

An entry script installed before the extension point ignores
`extensions.json` without a word. The hash check of step 2 is what tells
such an install apart: its `dispatch-pre-tool.mjs` is not the file the
contract file lists, or there is no contract file at all.

This module does steps 1 to 4, with Node built-ins only and without
loading any file of the repository's. It takes the entry the plugin wrote
and returns `{ problems, warnings }`; rely on the gate only when `problems`
is empty, and show `warnings` to the person. kh-harness's tests run it
against real installs holding the worked extension below: it accepts a
fresh install and one whose files have CRLF line endings, and refuses an
edited listed file; a missing registration, one with `async: true`, with a
`timeout` key, under the matcher `Bash`, or only in `settings.local.json`;
`disableAllHooks: true` in either settings file; no extensions file, an
extensions file without the entry, a malformed one, and a module edited by
one byte; a repeated key and a contract file that is a link. It warns of
`onFailure: "allow"`.

```js
// Checks that the kh-harness install in a repository honours contract 1,
// and that a plugin's own extension is in place to run before every tool
// call, before the plugin relies on either. Node built-ins only; it loads no
// file of the repository's. `checkContract1(root, extension)` takes the
// entry the plugin wrote for its extension, `{ id, version, module, sha256,
// onFailure }`, and returns `{ problems, warnings }`: one sentence per
// failed check, and one per risk the caller should show. Rely on the gate
// only when `problems` is empty.
import { createHash } from 'node:crypto';
import { closeSync, constants, fstatSync, lstatSync, openSync, readSync, realpathSync } from 'node:fs';
import { join, sep } from 'node:path';

const CONTRACT_PATH = '.claude/kh-harness/contract.json';
const EXTENSIONS_PATH = '.claude/kh-harness/extensions.json';
const ENTRY_SCRIPT = '.claude/scripts/dispatch-pre-tool.mjs';
const ENTRY_ARG = '${CLAUDE_PROJECT_DIR}/.claude/scripts/dispatch-pre-tool.mjs';
const LISTED_PATH = /^\.claude\/scripts\/[A-Za-z0-9._-]+\.mjs$/;
const ENTRY_KEYS = ['id', 'version', 'module', 'sha256', 'onFailure'];
const ID = /^[a-z][a-z0-9-]{0,63}$/;
const VERSION = /^[0-9A-Za-z][0-9A-Za-z.+-]{0,31}$/;
const MODULE = /^\.claude\/[A-Za-z0-9._/-]+\.mjs$/;
const SHA256 = /^[0-9a-f]{64}$/;
const MiB = 1024 * 1024;
const FLAGS = constants.O_RDONLY | (constants.O_NOFOLLOW ?? 0) | (constants.O_NONBLOCK ?? 0);

/** SHA-256 hex of `bytes` with each CRLF made LF, in one pass. */
export function lfSha256(bytes) {
  const lf = Buffer.from(bytes.toString('latin1').replace(/\r\n/g, '\n'), 'latin1');
  return createHash('sha256').update(lf).digest('hex');
}

/** True when `path` is a directory and not a link. */
function isRealDirectory(path) {
  try {
    const st = lstatSync(path);
    return st.isDirectory() && !st.isSymbolicLink();
  } catch {
    return false;
  }
}

/** True when nothing at all is at `path`. */
function isAbsent(path) {
  try {
    lstatSync(path);
    return false;
  } catch (error) {
    return error?.code === 'ENOENT';
  }
}

/** The bytes of the regular file at `path`, at most `maxBytes`, read from
 * one descriptor that does not follow a link at the file; null for anything
 * else. */
function readFile(path, maxBytes) {
  let fd;
  try {
    if (lstatSync(path).isSymbolicLink()) return null;
    fd = openSync(path, FLAGS);
  } catch {
    return null;
  }
  try {
    if (!fstatSync(fd).isFile()) return null;
    const buf = Buffer.alloc(maxBytes + 1);
    let length = 0;
    for (let n; length < buf.length && (n = readSync(fd, buf, length, buf.length - length, null)) > 0;) length += n;
    return length > maxBytes ? null : buf.subarray(0, length);
  } catch {
    return null;
  } finally {
    closeSync(fd);
  }
}

/** The JSON value of the file at `path`, or undefined when it cannot be
 * read or parsed. */
function readJson(path, maxBytes) {
  try {
    return JSON.parse(readFile(path, maxBytes).toString('utf8'));
  } catch {
    return undefined;
  }
}

const isObject = value => value !== null && typeof value === 'object' && !Array.isArray(value);
const hasExactly = (value, keys) => isObject(value) && Object.keys(value).length === keys.length && keys.every(k => Object.hasOwn(value, k));

/** True when `settings` registers the PreToolUse entry script exactly as
 * `apply` writes it, on every tool call: an element of `hooks.PreToolUse`
 * with no key but `matcher` and `hooks`, a `matcher` that is absent, `""`
 * or `"*"`, and a hook object of exactly `type`, `command` and `args`. Any
 * other key on the hook (`async`, `timeout`, `if`, `onFailure`, …) can stop
 * it blocking, or running, on some call. */
function entryScriptRegistered(settings) {
  const elements = settings?.hooks?.PreToolUse;
  return Array.isArray(elements) && elements.some(element => isObject(element)
    && Object.keys(element).every(k => k === 'matcher' || k === 'hooks')
    && (element.matcher === undefined || element.matcher === '' || element.matcher === '*')
    && Array.isArray(element.hooks) && element.hooks.some(hook => hasExactly(hook, ['type', 'command', 'args'])
      && hook.type === 'command' && hook.command === 'node'
      && Array.isArray(hook.args) && hook.args.length === 1 && hook.args[0] === ENTRY_ARG));
}

const isEntry = e => hasExactly(e, ENTRY_KEYS)
  && typeof e.id === 'string' && ID.test(e.id)
  && typeof e.version === 'string' && VERSION.test(e.version)
  && typeof e.module === 'string' && e.module.length <= 200 && MODULE.test(e.module)
  && e.module.split('/').every(segment => segment !== '' && !segment.endsWith('.') && !segment.endsWith(' '))
  && !e.module.toLowerCase().startsWith('.claude/scripts/')
  && typeof e.sha256 === 'string' && SHA256.test(e.sha256)
  && (e.onFailure === 'block' || e.onFailure === 'allow');

/** True when `list` is an extensions file kh-harness reads as `ok`. */
function isExtensionsFile(list) {
  if (!Array.isArray(list) || list.length > 8 || !list.every(isEntry)) return false;
  const ids = list.map(e => e.id);
  const modules = list.map(e => e.module.toLowerCase());
  return new Set(ids).size === ids.length && new Set(modules).size === modules.length;
}

const isUnder = (path, dir) => path.startsWith(dir + sep);

/** True when the module `rel` names is a regular file under the
 * repository's real `.claude/`, outside its real `.claude/scripts/`, of at
 * most 1 MiB, whose bytes hash to `sha256`. */
function moduleMatches(root, rel, sha256) {
  try {
    const realRoot = realpathSync.native(root);
    const claude = realpathSync.native(join(realRoot, '.claude'));
    const scripts = realpathSync.native(join(realRoot, '.claude/scripts'));
    const real = realpathSync.native(join(realRoot, rel));
    if (!isUnder(claude, realRoot) || !isUnder(real, claude) || isUnder(real, scripts)) return false;
    const bytes = readFile(real, MiB);
    return bytes !== null && lfSha256(bytes) === sha256;
  } catch {
    return false;
  }
}

function contractProblems(root) {
  const bytes = readFile(join(root, CONTRACT_PATH), 65536);
  if (bytes === null) return [`${CONTRACT_PATH} is missing, a link, not a regular file, or larger than 65536 bytes`];
  const text = bytes.toString('utf8').replace(/\r\n/g, '\n');
  let file;
  try {
    file = JSON.parse(text);
  } catch {
    return [`${CONTRACT_PATH} is not JSON`];
  }
  // Written by kh-harness as JSON.stringify(value, null, 2) and a newline;
  // anything else, such as a repeated key, is not a file it wrote.
  if (!isObject(file) || `${JSON.stringify(file, null, 2)}\n` !== text) return [`${CONTRACT_PATH} is not in the form kh-harness writes`];
  if (file.contract !== 1) return [`${CONTRACT_PATH} does not say contract 1`];
  if (!isObject(file.files) || !Object.hasOwn(file.files, ENTRY_SCRIPT)) return [`${CONTRACT_PATH} does not list ${ENTRY_SCRIPT}`];
  const problems = [];
  for (const [path, sha256] of Object.entries(file.files)) {
    if (!LISTED_PATH.test(path)) {
      problems.push(`${CONTRACT_PATH} lists a path that is not an installed script`);
      continue;
    }
    const installed = readFile(join(root, path), 4 * MiB);
    if (installed === null || lfSha256(installed) !== sha256) problems.push(`${path} is not the file contract 1 speaks for`);
  }
  return problems;
}

function settingsProblems(root) {
  const problems = [];
  const settings = readJson(join(root, '.claude/settings.json'), MiB);
  const localPath = join(root, '.claude/settings.local.json');
  const local = isAbsent(localPath) ? {} : readJson(localPath, MiB);
  if (!isObject(settings)) problems.push('.claude/settings.json could not be read');
  if (!isObject(local)) problems.push('.claude/settings.local.json could not be read');
  if (settings?.disableAllHooks === true) problems.push('.claude/settings.json sets disableAllHooks');
  if (local?.disableAllHooks === true) problems.push('.claude/settings.local.json sets disableAllHooks');
  if (isObject(settings) && !entryScriptRegistered(settings)) problems.push(`.claude/settings.json does not register ${ENTRY_SCRIPT} on PreToolUse for every tool call, as apply writes it`);
  return problems;
}

function extensionProblems(root, extension) {
  const bytes = readFile(join(root, EXTENSIONS_PATH), 65536);
  if (bytes === null) return [`${EXTENSIONS_PATH} is missing, a link, not a regular file, or larger than 65536 bytes`];
  let list;
  try {
    list = JSON.parse(bytes.toString('utf8'));
  } catch {
    list = undefined;
  }
  if (!isExtensionsFile(list)) return [`${EXTENSIONS_PATH} is not an extensions file as contract 1 describes one, so every tool call is blocked`];
  const listed = list.find(e => e.id === extension.id);
  if (listed === undefined || ENTRY_KEYS.some(k => listed[k] !== extension[k])) return [`${EXTENSIONS_PATH} does not list the extension ${extension.id} as expected`];
  return moduleMatches(root, listed.module, listed.sha256) ? [] : [`the module of ${listed.id} does not hash to its recorded sha256`];
}

export function checkContract1(root, extension) {
  for (const dir of ['.claude', '.claude/kh-harness', '.claude/scripts']) {
    if (!isRealDirectory(join(root, dir))) return { problems: [`${dir} is missing, a link, or not a directory`], warnings: [] };
  }
  const problems = [...contractProblems(root), ...settingsProblems(root), ...extensionProblems(root, extension)];
  const warnings = extension.onFailure === 'allow'
    ? [`the extension ${extension.id} has onFailure "allow": if its module is missing or differs, its gate is off and only the person is told, once per session`]
    : [];
  return { problems, warnings };
}
```

It is deliberately strict: it also refuses a `.claude/settings.json` that
is a link, which kh-harness accepts.

## The rules registry

`docs/harness/RULES.md` holds the repository's rules, written by its owner.
kh-harness never writes a rule there; another plugin may read it and may
write rules into it with the owner's agreement.

- Text inside HTML comments (`<!-- … -->`) is not read.
- Each rule starts with a level-2 heading, `## <id> <separator> <rule>`.
  `<id>` is one token: a letter, then letters, digits, `_`, `.` or `-`.
  `<separator>` is a run of em dashes, en dashes or hyphens with white
  space on both sides, or white space alone. `<rule>` is the rest of the
  line.
- Under it, one bullet per key: `- key: value` (or `* key: value`). A key
  is matched without regard to case, `-` or `_`, so `enforced-by`,
  `Enforced_By` and `enforcedBy` are one key.
- Every level-2 heading (a line starting `## `, or `##` alone) starts a
  rule; one not of that form is reported as a problem by `detect`, and the
  lines under it belong to no rule. A plugin writing into the file must
  not add any other level-2 heading. Level-3 and deeper headings are not
  headings to the parser.
- A rule ends at the next level-2 heading. Lines that are not bullets are
  ignored. A second rule with an id already used is reported and ignored.
- Keys whose names kh-harness does not read are ignored without a report.

| Key | Values | What kh-harness does with it |
|---|---|---|
| `why` | one line | read, not used |
| `enforced-by` | `deny`, `hook`, `lint`, `test`, `critic`, `ci`, `review`, `officer` or `none` | counted per value; any other value, or none, is reported and counted as `none` |
| `pointer` | a repository path, `settings:permissions.deny` or `settings:hooks.<Event>` | `detect` reports a pointer that does not resolve; required for every enforcer but `none` and `review` |
| `verify` | a command for a person to run | read, never run |
| `priority` | `high` or `normal` (anything else is `normal`) | `high` rules are re-told to Claude first |
| `status` | `active` or `superseded` | a superseded rule is not counted; another value is reported |
| `last-verified` | `YYYY-MM-DD` | another value is reported |
| `approval` | `owner` or `agent` | accepted and ignored: any value, never reported |

**`enforced-by: officer`** names a check that another tool runs. Its

repository (an absolute path, a `..` path, or any `settings:` pointer), or
leads outside through a link. It never runs the officer, so it never says
whether one passes.

The keys `origin`, `evidence`, `approved-sha256` and `approved-action` are
the kit's own, for entries in `docs/harness/LEARNED.md`; do not write them.

## The `PreToolUse` extension point

Another plugin can run its own check before every tool call, inside
kh-harness's `PreToolUse` hook, by listing a module in
`.claude/kh-harness/extensions.json`. The extension can allow the call or
block it with a message the model is shown.

### The extensions file

- **kh-harness never writes it**, never records it in its manifest, and
  `uninstall` leaves it and its modules in place. The plugin that
  registers an extension writes the file, and records it in its own
  manifest.
- `apply` installs the permission rule `Edit(/.claude/kh-harness/**)` in
  `.claude/settings.json`, which stops Claude Code's file-editing tools
  changing anything under `.claude/kh-harness/`. A plugin's installer
  therefore writes the file from its own process, such as a script the
  owner runs, not through an agent's edit. The rule does not stop a shell
  command.
- It is a JSON array of at most 8 entries, at most 65,536 bytes, in UTF-8
  with no byte order mark. Each entry is an object with exactly these five
  keys; write each key once, since a repeated key keeps the last value:

| Key | Value |
|---|---|
| `id` | the extension's name, shown in every message about it: `/^[a-z][a-z0-9-]{0,63}$/` |
| `version` | the extension's version, shown by `detect`: `/^[0-9A-Za-z][0-9A-Za-z.+-]{0,31}$/` |
| `module` | the module's path: `.claude/` then letters, digits, `.`, `_`, `/` or `-`, ending in `.mjs`, at most 200 characters; no segment empty or ending in `.` or a space (so no `.` or `..` segment); not under `.claude/scripts/`, compared without regard to case |
| `sha256` | the module's hash by [the hashing rule](#the-hashing-rule), 64 lower-case hex digits |
| `onFailure` | `"block"` or `"allow"`: what happens to a call when this extension cannot decide it |

No two entries may share an `id`, or a `module` compared without regard to
case.

**A file that breaks any of these rules blocks every tool call** with:

    kh-harness: .claude/kh-harness/extensions.json cannot be used (<problem>), so every tool call is blocked. Repair or remove the file outside this session.

The file is judged in this order, and the first problem found is named:

1. `.claude/kh-harness` must be a directory and not a link, and so must
   `.claude`. A `.claude` that is a link counts only when an extensions file
   is reached through it: then every call is blocked. A `.claude` link
   through which nothing is at `kh-harness/extensions.json` means no
   extensions file. No `.claude` or no `.claude/kh-harness` means no file.
2. The file must be a regular file, not a link, of at most 65,536 bytes.
3. It must be JSON, and an array, of at most 8 entries.
4. No repeated `id`, then no repeated `module`.
5. Each entry, in order, must be as the table says.
6. No entry's `module` may be under `.claude/scripts/`, where the kit keeps
   its own hooks.

A file holding `[]` lists no extension and blocks nothing.

### How each extension is run

On each `PreToolUse` call whose hook input names a tool, the entry script
`.claude/scripts/dispatch-pre-tool.mjs` runs every listed extension, in file
order, each one whether or not an earlier one blocked, and then the kit's
own gate hook and session log. For each entry:

1. **The module is judged**, in this order: `missing` when nothing is at its
   path; `outside` when the repository's real `.claude/` is not inside the
   real repository root, or the module's real path is not under the real
   `.claude/`, or is under the real `.claude/scripts/` (a module path may
   pass through links as long as these hold); `unreadable` when it is not a
   regular file or is larger than 1,048,576 bytes on disk; `differs` when
   its hash is not the recorded `sha256`. Otherwise it matches.
2. **It is loaded from the bytes that were hashed**, not from its path: the
   bytes, with CRLF made LF, are imported as a `data:` URL. So an extension
   is **one self-contained file**: it may import `node:` built-ins and
   nothing else. A relative import (`./x.mjs`) or a package import fails to
   load. `import.meta.url` is that `data:` URL, not the file's path; find
   the repository through `process.env.CLAUDE_PROJECT_DIR`, which Claude
   Code sets. Loading must finish within 1 second (`loadMaxMs`), a bound
   that exists for a top-level `await` that never settles.
3. **`preToolUse(payload)` is called**, synchronously. It must be a named
   export that is a function. `payload` is a fresh `structuredClone` of
   the hook input Claude Code sent (its `session_id`, `cwd`,
   `hook_event_name`, `tool_name`, `tool_input`, `tool_use_id` and the
   rest), so a change to it reaches nothing else.
4. **The result** must be exactly one of:
   - `{ decision: 'allow' }`
   - `{ decision: 'block', message }`, where `message` is a string of 1 to
     300 characters (`messageMax`, counted as JavaScript string length).

   The result must be a plain object (its prototype `Object.prototype`)
   with exactly those own keys. A promise is not a result: an `async`
   function's result is malformed, and nothing is awaited.

A block message is cleaned before the model sees it: each run of tabs, CR,
LF, U+0085, U+2028 and U+2029 becomes one space; ANSI sequences, control
characters and invisible formatting characters are removed; `<` and `>`
become `&lt;` and `&gt;`; text shaped like a credential is masked; the ends
are trimmed. A message that is empty after cleaning, or longer than 300
characters after cleaning, is a malformed result.

**What the model is shown for a block.** The hook writes one JSON object on
one line and exits 0. Its deny part is fixed: for a block alone it is

    {"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"kh-harness extension <id>: <cleaned message>"}}

Several blocks are joined by a newline, in file order, and any denial from
the kit's own gate follows them. The same object may also carry a
`systemMessage` (a notice for the person, such as an `onFailure: "allow"`
notice or one of the gate hook's) and a `hookSpecificOutput.additionalContext`
(from the gate hook); a reader must not expect the deny part alone. A call denied by
an extension is still seen by the gate hook and the session log.

What kh-harness does while an extension runs:

- `process.exit` throws while the module loads and while `preToolUse`
  runs, and is put back after.
- Once the first extension whose module matches is about to load,
  `process.stdout.write` and
  `process.stderr.write` write nothing for the rest of the process, so
  `console.log` and similar output are dropped, during the call or later.
  The kit writes its own output through the streams' writes as they were
  before any extension ran.
- An exception thrown later from a callback, or a rejection nobody
  handles, is ignored: it stops neither the halves after it nor the output.

There is no time limit on the call itself: a timer cannot interrupt
synchronous code. An extension may read small files. It must not start a
process, wait on anything, write to standard output or standard error, or
exit.

### When an extension cannot decide: `onFailure`

Each of these is a failure of that entry, with the reason shown:

| Failure | Reason in the message |
|---|---|
| nothing at the module's path | `its module file is missing` |
| the hash does not match | `its module file does not match the sha256 recorded for it` |
| the module is not under the real `.claude/`, or is under `.claude/scripts/` | `its module is not a file under .claude/ in this repository` |
| not a regular file, over 1,048,576 bytes, or its path cannot be resolved | `its module file could not be read` |
| the import fails: a syntax error, an import that is not `node:`, a throw or `process.exit` at load, a load over 1 second | `its module could not be loaded` |
| no `preToolUse` function exported | `its module exports no preToolUse function` |
| `preToolUse` throws, calls `process.exit`, or returns an object whose getter throws when the result is read | `its preToolUse threw` |
| any result but the two shapes above, a promise, or a message that fails the rules above | `its preToolUse returned neither an allow nor a block with a usable message` |

With `onFailure: "block"`, the call is denied, every time, with:

    kh-harness extension <id>: <reason>, so this call is blocked (onFailure: block). Reinstall the plugin that registered it, or remove its entry from .claude/kh-harness/extensions.json outside this session.

With `onFailure: "allow"`, the call goes ahead, and the person (not the
model) is told once per session, as a `systemMessage`:

    kh-harness extension <id>: <reason>, so it checks no call (onFailure: allow).

The wording of these two texts and of the reasons is not promised; that
each names the entry's `id` is.

### When the kit's own files cannot run the extensions

When an extensions file is in play (anything at its path, a `.claude`
that is a file, a `.claude/kh-harness` that is a link or not a directory,
or a `.claude` link through which something is at its path), the entry
script refuses the core `harness-dispatch.mjs` when it is missing, cannot
be loaded, or lacks a function export named `dispatch` or `half`, and the
loader `harness-extensions.mjs` when it is missing, cannot be loaded, or
lacks a function export named `extensionsHalf`. Then every call is blocked
with:

    kh-harness: .claude/scripts/<file> <problem> while .claude/kh-harness/extensions.json exists, so every tool call is blocked. Run kh-harness apply --yes, or remove the extensions file, outside this session.

The entry script judges these files by those exports alone. A core or a
loader older than the entry script that still has them is not detected:
beside the entry script of this kit, a core from before the extension
point's output handling lets an extension's block vanish, with no output
and exit 0, so the call goes ahead. This is why
[step 2](#what-a-plugin-must-check-before-relying-on-contract-1), the hash
check of every listed file, is mandatory. *(Known defect, to be fixed: the
entry script does not yet refuse an older core or loader that has the
exports.)*

Without an extensions file, the loader is never loaded, and the kit's own
hooks behave as they do without the extension point. A loader that is
missing still leaves the gate and the log running beside the block; a core
that is missing leaves nothing running.

### What `detect` reports

`detect` lists, under `P5.extensions`, each extension with its `id`,
`version`, `module`, whether the module matches its `sha256`, and its
`onFailure`, and says whether `dispatch-pre-tool.mjs` is registered and
whether the installed entry script, core and loader are this kit's. It
never loads a module. It never prints the `sha256`. It is a diagnostic for
people: neither its wording nor its states are promised.

Extensions are not part of the harness identity the session log records
for a session: a session's log does not show which extensions ran.

## Limits

An extension runs inside the kit's `PreToolUse` hook process, as code the
repository holds. The kit contains an extension's accidental faults: each
of these is that entry's `onFailure`, and the kit's own gate still runs
after it.

- an error thrown while it loads or runs;
- a call to `process.exit` while it loads or runs;
- a result of the wrong shape, or a promise it returns;
- a block message over 300 characters, as returned or once cleaned;
- an exception or rejection it leaves behind in a callback;
- output written through `process.stdout.write`, `process.stderr.write`
  or `console`, at any time;
- a load that does not finish within 1 second (`loadMaxMs`).

A run that some half leaves unsettled is written, with what was gathered,
when the event loop has nothing left to do or at the run deadline, 120
seconds.

The kit does not contain an extension that sets out to escape it. An
extension, once its hash is recorded, can still defeat the hook:

- by writing to the standard output descriptor directly
  (`fs.writeSync(1, …)`), or through the stream's internals
  (`process.stdout._write`, `process.stdout.end()`);
- by calling `process.reallyExit`, or `process.exit`, `process.abort` or
  `process.kill` from a callback that runs after its call returned;
- by looping forever synchronously, which nothing in the process can end;
  Claude Code's hook timeout (600 seconds by default) ends it, and a
  `PreToolUse` hook that times out does not block the call;
- by replacing a global the kit relies on, such as `JSON.stringify` or
  `structuredClone`: extensions share one `globalThis` with each other and
  with the kit.

When the hook ends without its output, Claude Code treats the call as not
decided by the hook, and the call goes ahead unless another rule stops it.

Two entries whose modules hold identical bytes share one module instance,
loaded once, so module-level state is shared between them.

An extension is therefore trusted code. Its hash proves only that the
module holds the bytes the file names.

The bounds, as `EXTENSION_LIMITS` in `.claude/scripts/harness-extensions.mjs`
holds them:

| Bound | Value |
|---|---|
| the extensions file | `fileMaxBytes` 65,536 bytes |
| entries | `entriesMax` 8 |
| a module on disk | `moduleMaxBytes` 1,048,576 bytes |
| a block message, as returned and once cleaned | `messageMax` 300 characters |
| loading a module | `loadMaxMs` 1,000 milliseconds |

## The extensions file and its modules are repository files

`.claude/kh-harness/extensions.json` and every module it lists are files in
the repository. A `git pull`, a merge or a checkout that adds or changes
them changes what runs before every tool call, with no step in kh-harness
asking anyone. The `sha256` the file records is integrity, not approval: it
shows that a module is the one the file names, not that anyone approved it,
since whoever changes the module can change the hash beside it. The hash
catches a stale or half-updated install. It is no defence against an agent
or a commit that edits both files. A plugin that needs its extension to be
approved must hold that approval somewhere a pull cannot change, and check
it itself.

## A worked extension

A module that stops the model editing `package-lock.json` by hand. Save it
as `.claude/acme-lockfile/guard.mjs`:

<!-- fixture: extension.mjs -->
```js
// .claude/acme-lockfile/guard.mjs: a kh-harness contract 1 PreToolUse
// extension. One self-contained file; it imports Node built-ins only.
import { basename } from 'node:path';

const EDITING_TOOLS = new Set(['Edit', 'MultiEdit', 'Write']);

export function preToolUse(payload) {
  const file = payload.tool_input?.file_path;
  if (EDITING_TOOLS.has(payload.tool_name) && typeof file === 'string' && basename(file) === 'package-lock.json') {
    return { decision: 'block', message: 'package-lock.json is written by npm install; do not edit it by hand.' };
  }
  return { decision: 'allow' };
}
```

Compute its hash by the hashing rule. In a POSIX shell, from the
repository root:

<!-- example: hash-command -->
```sh
node -e "const c=require('node:crypto'),f=require('node:fs');const b=f.readFileSync(process.argv[1]).toString('latin1').replace(/\r\n/g,'\n');console.log(c.createHash('sha256').update(b,'latin1').digest('hex'))" .claude/acme-lockfile/guard.mjs
```

Write `.claude/kh-harness/extensions.json` from the installer's own
process:

<!-- fixture: extensions.json -->
```json
[
  {
    "id": "acme-lockfile",
    "version": "1.0.0",
    "module": ".claude/acme-lockfile/guard.mjs",
    "sha256": "02a911c8dfd658c85a27d66b6d5e535807a45bbabc0fb0904cd7eddee59fc281",
    "onFailure": "block"
  }
]
```

Then verify:

1. Run `checkContract1(root, entry)` (above), with `entry` the object the
   installer wrote: it returns `{ problems: [], warnings: [] }`.
2. Run the entry script as Claude Code does, with the hook input on
   standard input and `CLAUDE_PROJECT_DIR` set to the repository. An
   `Edit` of `src/index.js` prints nothing (the call is allowed). An
   `Edit` of `package-lock.json` prints the denial
   `kh-harness extension acme-lockfile: package-lock.json is written by npm install; do not edit it by hand.`

## Appending to the session log

A plugin can add one event to a session's log through `recordExternalEvent`,
exported by the installed `.claude/scripts/harness-log.mjs`. Import it only
after the checks above, since importing the file runs it:

```js
import { join } from 'node:path';
import { pathToFileURL } from 'node:url';

const { recordExternalEvent } = await import(pathToFileURL(join(root, '.claude/scripts/harness-log.mjs')).href);
const result = recordExternalEvent(root, sessionId, { source: 'kh-orchestration', type: 'officers.run', data: { failed: ['V8'] } });
```

`recordExternalEvent(root, sessionId, { source, type, data })` returns
`{ recorded: true }` or `{ recorded: false, reason }`, and never throws.

| Argument | Accepted |
|---|---|
| `root` | the repository root, an absolute path |
| `sessionId` | 1 to 200 characters from `A-Z`, `a-z`, `0-9`, `_` and `-`: the `session_id` of the hook input the plugin was given |
| `source` | the plugin's name: `/^[a-z][a-z0-9-]{0,63}$/` |
| `type` | what happened: `/^[A-Za-z][A-Za-z0-9._-]{0,63}$/` |
| `data` | a value whose `JSON.stringify`, taken once, is a JSON object of at most 16,384 bytes of UTF-8 (`EXTERNAL_DATA_MAX_BYTES`), nested at most 32 levels deep (`EXTERNAL_DATA_MAX_DEPTH`; the object itself is level 1, and each object or array inside adds one) |

The line written, minus its `ts` (an ISO time) and `pid`, for the call
above with the session id `fixture`:

<!-- fixture: plugin-event.json -->
```json
{
  "schema": 1,
  "type": "plugin_event",
  "session_id": "fixture",
  "source": "kh-orchestration",
  "kind": "officers.run",
  "data": { "failed": ["V8"] }
}
```

Its keys are `schema`, `ts`, `pid`, `type`, `session_id`, `source`, `kind`
and `data`, in that order. `type` is always `plugin_event`, and `kind` is
the caller's `type`. Nothing in `data` can set the line's own keys.

Nothing is recorded, and `reason` is one of these fixed texts. The checks
run in this order, and the first that fails is reported:

<!-- fixture: refusals.json -->
```json
[
  "no safe session id",
  "root must be an absolute path",
  "the session log is not enabled for this repository",
  "data must be a JSON object",
  "source must be lower-case letters, digits and hyphens, starting with a letter, at most 64 characters",
  "type must be letters, digits, dot, underscore and hyphen, starting with a letter, at most 64 characters",
  "data is larger than 16384 bytes",
  "data must be nested at most 32 levels deep",
  "the event could not be written"
]
```

- `no safe session id`: `sessionId` is not as above.
- `root must be an absolute path`.
- `the session log is not enabled for this repository`: the log is off by
  default. This machine's owner turns it on per repository with
  `node scripts/log.mjs <repo> enable`, run from the kh-harness checkout,
  which records it in the data directory outside the repository
  (`$KH_DATA_DIR` when it is absolute, otherwise `~/.claude/kh-harness`,
  read from the calling process's environment). Nothing is created while
  it is off. Do not treat this as an error of the plugin's own run.
- `data must be a JSON object`: the third argument is not an object, or is
  an array or `null`;
  or, after `source` and `type` are checked, `data` has no JSON (a cycle, a
  BigInt, a getter or `toJSON` that throws) or its JSON is not an object.
- the `source` and `type` texts: the value is not in its set.
- `data is larger than 16384 bytes`, checked before the depth.
- `data must be nested at most 32 levels deep`.
- `the event could not be written`: an I/O failure, or a link at the log
  directory, its sessions directory or the session's file.

The line is written in one append, so lines from processes writing at once
interleave whole, in no promised order. An event is masked as the kit's own
events are, so do not expect it to read back byte for byte:

- every key and string, at any depth, is masked: text shaped like a
  credential, a value under a credential-named key, and a value after a
  credential flag in an array become `***`; keys that mask to the same text
  get `#2`, `#3` suffixes; ANSI sequences are removed. A `source` or `type`
  shaped like a credential is stored as `***`;
- JSON drops `undefined`, functions and symbol keys, turns `NaN` into
  `null`, and stores a `Map` or other object by its JSON (`{}` for a `Map`).

**Retention.** `data` is content. It is removed, and `contentExpired: true`
set, once the session is sealed and its last event is older than the
content retention period (90 days by default, `contentRetentionDays`). `source`, `kind`, `type`,
`session_id`, `schema`, `ts` and `pid` are kept for as long as the sealed
session is. Put nothing in `source` or `type` that must expire.

What a plugin must not assume:

- that the session id names a session that is running: it is not checked,
  and an id that names none starts a file;
- that `root` is a repository the caller owns: any absolute path whose log
  is enabled can be written, and only under that repository's directory of
  the data directory;
- that strings in `data` are safe to show: they are masked, not cleaned of
  control characters or of text shaped like an instruction. A reader that
  shows `data` must present it as data. No kh-harness command reads `data`
  today;
- that no blob is written: none is at the default `inlineCapBytes`
  (65,536), but an owner who lowers it below 16,384 sends long strings to
  blobs, as for the kit's own events;
- that an object in `data` holding `truncated: true` and a 64-hex `blob` is
  left alone: the log's blob sweep reads it as a reference to one of its
  own blobs. Do not use that shape;
- that a credential split across two strings is masked: the mask reads one
  string at a time.

A half-updated install, with a new `harness-log.mjs` beside an older
`harness-seal.mjs`, records the event but never expires its `data`. Call
`recordExternalEvent` only when the hash check of the contract file passes.

## What is not promised

- Every installed file other than those named here, and every name inside
  them other than `recordExternalEvent`, `EXTERNAL_DATA_MAX_BYTES` and
  `EXTERNAL_DATA_MAX_DEPTH` in `harness-log.mjs` and `EXTENSION_LIMITS` in
  `harness-extensions.mjs`.
- Which files `files` lists, beyond the entry script; their hashes, which
  change with every kit version.
- The wording of every message other than the fixed texts stated as fixed
  here: the extension block line, the deny output's shape and the
  `recordExternalEvent` reasons.
- Anything `detect` reports: its wording, its states, `detect --json` and
  `docs/harness/detect.json`. `detect` is a diagnostic for people.
- The layout of the data directory and of the session log, beyond the
  `plugin_event` line.
- Timing: how long a hook takes, and when sealing and retention run.
- That Claude Code runs the hooks the settings register.

## Open questions for the owner

- **`onFailure: "block"` on the `PreToolUse` registration.** Claude Code's
  hooks reference describes an `onFailure` field on a command hook
  registration, `"continue"` or `"block"` (Claude Code 2.1.295 or later).
  With `"block"`, a hook that cannot start, exits with a code other than 0
  or 2, or times out blocks a `PreToolUse` call instead of letting it go
  ahead. On the `dispatch-pre-tool.mjs` registration it would turn every
  case in [Limits](#limits) where the hook ends without its output into a
  block. kh-harness does not set it: every registration it writes is
  `node` with exactly one argument and nothing else, and its `detect` and
  `uninstall` recognise that form. Whether the kit should write it, and
  what a plugin may then rely on, is the owner's decision, and a change to
  the registration a plugin checks would need a new contract number.
