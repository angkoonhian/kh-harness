Research date: 2026-11-18. Every page was read on that date. Formats cited here (hook payloads, OpenTelemetry names, transcript layout, third-party file formats) change between versions and must be re-checked against the installed version before a tool relies on them.

## 1. What does Claude Code itself record and expose as of late 2026?

### Takeaway
Claude Code exposes four local records: hook payloads (33 events, documented field by field), a plaintext JSONL transcript per session whose location is documented but whose entry format is officially "internal" and unstable, OpenTelemetry metrics, events and beta traces (content redacted by default), and the `/insights` report built from local transcripts. The documented blind spots for a learning layer are: no hook fires when the user interrupts a turn or cancels a running tool, the user declining a permission prompt in a non-auto mode has no dedicated hook, and the only Anthropic-supported ways to read a session are `/export`, `claude -p --resume`, `transcript_path` from a hook, and the Agent SDK, not parsing the JSONL.

**Transcript files**

- [vendor doc] (raw) "By default, Claude Code stores transcripts as JSONL at `~/.claude/projects/<project>/<session-id>.jsonl`, where `<project>` is your working directory path with non-alphanumeric characters replaced by `-`"; names over 200 characters are truncated with a hash appended. — [Claude Code docs, Manage sessions](https://code.claude.com/docs/en/sessions.md)
- [vendor doc] (raw) "Each line is a JSON object: a message, a tool use or result, a record of a request Claude Code sent the model, or a metadata entry. The entry format is internal to Claude Code and changes between versions, so scripts that parse these files directly can break on any release. To build on session data, use `/export` or the script interfaces instead." — [Manage sessions](https://code.claude.com/docs/en/sessions.md)
- [vendor doc] (raw) The supported script interfaces are: `claude -p` with `--output-format json` or `stream-json`; `claude -p --resume <session-id>` to ask an existing session a question; `transcript_path` from hooks and status-line commands ("A `SessionEnd` hook can archive the transcript when a session ends"); and the Agent SDK. — [Manage sessions](https://code.claude.com/docs/en/sessions.md)
- [vendor doc] (raw) Related files under `~/.claude/`: `projects/<project>/<session>/subagents/` (subagent transcripts, same format), `projects/<project>/<session>/tool-results/` (large tool outputs spilled to files), `file-history/<session>/` (pre-edit snapshots for the 100 most recent checkpoints), `debug/`, `history.jsonl` (typed prompts with timestamp and project path), `usage-data/` (`/insights` reports and cached per-session analysis), `stats-cache.json`. — [Claude Code docs, .claude directory](https://code.claude.com/docs/en/claude-directory.md)
- [vendor doc] (raw) The transcript "can also hold what Claude Code sends the model with your messages": the system prompt, tool definitions, request parameters, and loaded instruction files such as CLAUDE.md. — [.claude directory](https://code.claude.com/docs/en/claude-directory.md)
- [vendor doc] (raw) After compaction, a resumed session loads the last summary plus later messages; "The messages that the last compaction summarized aren't loaded again." Two processes resuming one session both write one transcript and "messages from one of them can be missing". Sessions from `claude -p` and the Agent SDK are left out of the picker and `--continue` but can be resumed by ID. — [Manage sessions](https://code.claude.com/docs/en/sessions.md)

### Inferences
- What a hook-only logger cannot see, from the documented payloads: (1) a user interrupt (Esc) of a turn, because `Stop` does not run on interrupt and no interrupt event exists; (2) cancellation of a running tool, which does not fire `PostToolUseFailure`; (3) the user answering "no" to a permission prompt outside auto mode, since `PermissionDenied` is auto-mode only and `PermissionRequest` records the ask (without `tool_use_id`) but not the answer; (4) assistant text between tool calls and thinking, which only the transcript holds; (5) token and cost figures per request, which are in the transcript and in OTel, not in hook payloads (except subagent totals in the Agent tool's `tool_response` and context estimates on model-switch and resume events). Items 1 to 3 are observable through OTel `tool_decision` (`source` = `user_abort` / `user_reject`, per round one) or by inference from the transcript.
- An interrupted turn can be inferred from hooks alone as a `UserPromptSubmit` whose `prompt_id` never receives a `Stop` or `StopFailure` before the next `UserPromptSubmit` or `SessionEnd`. That is an inference from the documented "does not run" rule, not a documented signal, and background work or a crash would look the same.
- `PostToolUseFailure.error` plus `tool_name` plus a normalised `tool_input` is enough to detect repeated identical failures deterministically; `InstructionsLoaded` with `load_reason` and `PreCompact`/`PostCompact` with `compact_summary` give exact "which rules were in context" and "what compaction kept" records without touching the transcript.
- Because the entry format is declared internal, a zero-dependency tool that parses `~/.claude/projects/**/*.jsonl` is building on an interface Anthropic says may break "on any release". The durable design is hooks as the primary record, with transcript parsing as an optional enrichment that records the Claude Code version per session and degrades to "not checked" on unknown line types.
- `SessionEnd`'s 1.5-second default budget, and the fact that plugin hook timeouts do not raise it, means end-of-session analysis must not run inside that hook from a plugin; it should only write a marker and leave analysis to the next `SessionStart` or an explicit command.
- `/insights` and the `/usage` fix shortcut show Anthropic's own loop shape: local history, LLM-labelled friction, a report, and a human-triggered change. Neither writes rules without the user acting.

### Gaps
- Characters 0 to 200,000 of the hooks page reached me only as model-written extractions; field lists there (for example `PostToolUse.tool_response` shapes) should be confirmed against the page before a schema is frozen. The `Setup`, `MessageDisplay`, `PostToolBatch` and `UserPromptExpansion` details were not examined beyond their field lists.
- No official list of transcript line types exists; `isSidechain`, summary and compaction-boundary entries, and whether `usage` repeats across streamed chunks remain unverified (unchanged from round one).
- `/insights` internals (facet names, models used, session filters) are documented only by third parties; the one deep-dive I tried to read (zolkos.com, February 2026) returned HTTP 404.
- The Agent SDK sessions page and the `stream-json` message schema were not read; `listSessions` / `getSessionMessages` signatures come only from the session-storage page.
- I found no Anthropic documentation of any memory "dreaming" feature; its existence and behaviour are unconfirmed.

## 2. What do other coding agents record and expose?

### Takeaway
Local, per-session JSONL (or JSON) records plus opt-in OpenTelemetry with prompts redacted by default is the common pattern (Codex, Gemini CLI, Cursor, OpenHands, SWE-agent). Three vendors have productised analysis on top: Factory Signals (daily LLM-judged friction and delight across sessions, feeding tickets and agent-written fixes), Devin Session Insights (per-session issue timeline, action items and a rewritten prompt), and Claude Code `/insights`. Cursor documents hooks whose event set closely mirrors Claude Code's and adds an explicit `failure_type`.

### Cited Findings

**OpenAI Codex**
- [vendor doc] (summarised) OpenTelemetry is off by default and configured in an `[otel]` table; exporters are `none`, `otlp-http`, `otlp-grpc`; "If `exporter = "none"` Codex records events but sends nothing." `log_user_prompt` defaults to `false` ("redact user prompts unless explicitly enabled"). Events: `codex.conversation_starts`, `codex.api_request`, `codex.sse_event`, `codex.websocket_request`, `codex.websocket_event`, `codex.user_prompt`, `codex.tool_decision`, `codex.tool_result`, and opt-in `codex.agent_response` and `codex.guardian_assessment`. — [Codex docs, advanced configuration](https://learn.chatgpt.com/docs/config-file/config-advanced) (redirect target of developers.openai.com/codex/config-advanced)

## 3. What is the standard practitioner method for turning traces into improvements?

### Takeaway
The standard method is qualitative error analysis: read real traces, write a free-text note on the first thing that went wrong in each (open coding), group notes into a named failure taxonomy and count (axial coding), repeat until new traces stop producing new categories, then fix what is cheap to fix and build evaluators only for failures that persist. Vendors have automated the clustering step (LangSmith Insights, Braintrust Topics, Docent, Factory Signals, Clio), but the practitioners who teach the method say LLMs should scale a taxonomy a human built, not invent it.

### Cited Findings

**Error analysis (Husain and Shankar)**
- [practitioner, 27 June 2025, modified 1 September 2026] (summarised) Error analysis is "the most important activity in evals." Steps: build a dataset of representative traces; open coding (free-text notes, likened to journaling; note the first failure because "upstream errors can cause downstream issues"); axial coding into a "failure taxonomy" with counts; iterate to "theoretical saturation". Annotate at least 30 traces yourself before reviewing agent suggestions; work from roughly 100 diverse traces. The annotator should be a domain expert acting as a "benevolent dictator". "You can use an LLM to help with" axial coding. — [Husain and Shankar, evals FAQ: error analysis](https://hamel.dev/blog/posts/evals-faq/why-is-error-analysis-so-important-in-llm-evals-and-how-is-it-performed.html)
- [practitioner] (summarised) "If the agent starts suggesting problems too early, its guesses can bias your judgment." Keep "some random traces in every batch"; for rare failures target "a specific tool sequence, unusually long traces, retries". Feedback-based sampling "misses problems that users do not report" and classifier-based sampling "favors problems the classifier already knows how to find." Suggested cadence: 100+ fresh traces per cycle, 10 to 20 outlier reviews weekly. — [Husain and Shankar, evals FAQ](https://hamel.dev/blog/posts/evals-faq/)
- [practitioner] (summarised) "Binary evaluations force clearer thinking and more consistent labeling." "Focus automated evaluators on failures that persist after fixing your prompts." Generic metrics "waste time and create false confidence when you use them as quality measures", though they can serve as "exploration signals". The authors report spending "60-80% of our development time on error analysis and evaluation." — [evals FAQ](https://hamel.dev/blog/posts/evals-faq/)
- [practitioner] (summarised) For agents: first "Treat the agent as a black box and decide whether it met the user's goal", then step-level diagnostics. A transition failure matrix: "Create a matrix where rows represent the last successful state and columns represent where the first failure occurred." Check tool name, arguments, result and resulting state separately; "A valid tool call can still be wrong if the user did not approve the action." CI datasets "are small (in many cases 100+ examples) and purpose-built"; when production shows a new failure pattern, add representative examples to CI. — [evals FAQ](https://hamel.dev/blog/posts/evals-faq/) (read from character 100,000)
- [practitioner] (summarised) On automation: "Always read through the raw traces yourself at the start." "Use LLMs to scale what you've learned, not to avoid looking at data." Automated prompt optimisation can improve known failures but cannot find new ones. — [evals FAQ](https://hamel.dev/blog/posts/evals-faq/)
- [practitioner, 24 June 2026] (summarised) A later note on Shankar's session: error analysis is "the most human-intensive part of evals because it requires you to read and annotate traces"; an "Error Discovery" skill "updates a failure-mode taxonomy as you annotate and checks earlier records for each new pattern" and picks the next examples by active learning. Principle: "Build an error taxonomy from human review instead of asking an LLM to invent one." — [Husain, "Automating Error Analysis"](https://hamel.dev/notes/llm/ai-product-engineering/evals-error-analysis.html)

**Anthropic guidance**
- [vendor blog, 9 January 2026] (summarised) "You won't know if your graders are working well unless you read the transcripts and grades from many trials." Sample transcripts weekly; convert user-reported failures and bug-tracker items into test cases; a near-zero pass rate "is most often a signal of a broken task, not an incapable agent." Anthropic "invested in tooling for viewing eval transcripts". Layers (automated evals, A/B tests, production monitoring, user feedback, manual transcript review, human studies) are compared to the Swiss cheese model: "no single evaluation layer catches every issue." — [Anthropic, "Demystifying evals for AI agents"](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

**Automated clustering and LLM transcript analysis**
- [vendor doc] (summarised) LangSmith Insights "automatically analyzes your traces to detect usage patterns, common agent behaviors, and failure modes." - [vendor doc] (summarised) Transluce Docent analysis plans combine deterministic query steps with LLM "Reading" steps. - [snippet] At launch Transluce reported Docent finding missing packages on InterCode, where adding them raised GPT-4o's solve rate from 68.6% to 78%, and a Cybench task whose flag was exposed in a Dockerfile. — [search summary of Transluce, "Introducing Docent"](https://www.lesswrong.com/posts/Mj276hooL3Mncs3uv/analyzing-long-agent-transcripts-docent)

- [snippet] Raindrop's default signals include Forgetting, Task Failure and User Frustration, detected by trained classifiers with regex as a cheap complement; one write-up's summary is that regex is "useful as one sensor, not sufficient as the only sensor." — [Raindrop docs, Signals](https://www.raindrop.ai/docs/platform/signals.md)

### Inferences
- The method maps onto a local layer in four artefacts: a trace store (hook log), an annotation record (one free-text note per reviewed session, first failure only), a taxonomy file (named failure modes with definitions and counts), and a small regression set (one minimal reproduction per persistent failure). None needs a hosted service; only LLM-assisted clustering needs a model call.
- The practitioners' ordering matters for a self-improving harness: human notes first (30 or more), LLM grouping second. A tool that has an LLM read transcripts and propose rules directly skips the step the method's authors treat as the source of validity, and round one's evidence (generated context files and self-generated skills do not help on average) points the same way.
- "Focus automated evaluators on failures that persist after fixing" is a promotion rule: a finding first becomes a direct fix; only a failure that recurs after the fix earns a permanent check. That matches round one's doc-then-enforcer escalation.
- The transition failure matrix translates to coding sessions as (last successful step type) by (first failing step type), for example Edit then Bash(test) failure, which hook logs can populate deterministically.
- Automated clustering tools all need the traces uploaded to the vendor (LangSmith explicitly uploads local histories first); OpenClio (97 stars, last push 2025-08-19) is the only open-source Clio-style clusterer I found and it looks dormant.

### Gaps
- Langfuse and Arize features for error analysis and clustering, Galileo, and Eugene Yan's writing were not retrieved. Braintrust and Raindrop are snippet-only. The Atla post on automating error analysis returned HTTP 404.
- No source reports measured agreement between LLM-generated failure taxonomies and human-built ones for coding-agent traces.
- The Docent open-source status and its support for Claude Code transcripts were not confirmed (the TransluceAI/docent repository exists with 149 stars, last push 2026-11-13, but I did not read it).

### Inferences
- Signal reliability falls into three classes. Structural counts with an unambiguous definition (same file edited N times, same tool call failing N times, same file read N times, N consecutive failures) are reproducible, but their thresholds (2, 3, 5, 10:1) are each author's choice and differ between tools: "retry loop" is 2+ in cctx and 3+ in claude-doctor, cc-analyze and friction-detector. Lexical signals (messages starting "no"/"wrong"/"wait", AFINN sentiment, keyword lists) are cheap and have no published precision; "no" opens many non-corrective messages. Judged signals (scope creep, premature stopping, outcome) need an LLM and inherit judge noise.
- The rules these tools generate illustrate the failure round one predicted: claude-doctor's output from 838 sessions is five generic behavioural exhortations that could be written without any data, are told rules with no enforcer, and add always-loaded prose.
- cctx's `--efficacy` is the only before/after check I found in this class. It is a single-arm before/after comparison of finding rates, so it is exposed to regression to the mean (rules are added after bad sessions) and to model or version changes, as round one's section 4 warns.
- Two design choices in the smallest tools are worth copying: lucemia's standard-library-only analyser shows the structural metrics need no dependencies, and Dhravidk's separation of "unmet" from "unverified" and its explicit refusal to re-add a rule that already exists and was ignored are the honest-reporting posture a "reports only what it checked" tool wants.
- Adoption suggests demand is for looking at sessions (viewers, search, cost: 1,200 to 19,000 stars) far more than for automated diagnosis (0 to 620 stars), and the most-starred diagnoser has had no push since April 2026.

### Gaps
- I read READMEs, not code; none of these tools' detectors was run or checked against labelled sessions, and I found no third-party evaluation of any of them.
- Not examined: agentsview's quality and friction-log documentation in detail, specstory's "Lore", the transcript-analysis and conversation-analyzer skills surfaced by search (one repository path returned 404), and awesome-claude-code's listings.
- No tool was found that validates a correction or frustration detector against human labels on Claude Code transcripts.

## 5. Which session signals indicate a harness defect rather than a model limitation?

### Takeaway
The strongest published operational rule is Cursor's: classify tool errors, treat unknown errors as harness bugs, and compare each tool's error rate with a per-tool, per-model baseline (round one). Beyond that, sources name the signals (repeated identical failures, retries, user pushback and rephrasing, abandonment, backtracking, context churn, permission prompts) and two 2026 studies measure how common pushback is, but no source validates a rule for attributing a given signal to the harness versus the model.

### Cited Findings
- [vendor blog, 30 April 2026, round one] Cursor classifies tool errors into `InvalidArguments`, `UnexpectedEnvironment`, `ProviderError`, `UserAborted`, `Timeout`; treats unknown errors as harness bugs; alerts on per-tool, per-model baselines because "different models may mess up tool calls at different rates"; and reads the user's next message (a pasted stack trace is "a reliable signal that it didn't" work). — [Cursor, "Continually improving our agent harness"](https://cursor.com/blog/continually-improving-agent-harness)
- [vendor blog] (summarised) Factory's friction categories are session-level signals attributed to the product: Error Events, Repeated Rephrasing, Escalation Tone, Platform Confusion, Abandoned Tool Flow, Backtracking, Context Churn. Its abstracted citation example is "user expressed frustration after third failed tool call". It states that after three rephrases there is "roughly a forty percent chance" of another, with no method given. — [Factory, "Signals"](https://factory.com/news/factory-signals)
- [vendor doc] (summarised) Devin's issue types point at the environment and task specification: build failures, environment configuration problems, incorrect codebase assumptions, scope ambiguity; its action items are "Machine setup" and "Repo config". — [Devin docs, Session Insights](https://docs.devin.ai/product-guides/session-insights.md)
- [vendor doc] (raw) Claude Code treats permission prompts as a measurable cost: `/insights` can estimate "how many permission prompts auto mode could have handled across those sessions." — [Claude Code docs, Manage costs](https://code.claude.com/docs/en/costs.md)
- [vendor doc] (raw) Claude Code distinguishes expected from unexpected cache rebuilds: compaction and tool-result clearing count as "expected rebuild", other misses name a likely cause such as "tool definitions changed". — [Manage costs](https://code.claude.com/docs/en/costs.md)
- [study, COLM 2026; v1 22 April 2026, v2 1 October 2026] (abstract, summarised) SWE-chat: almost 18,000 real sessions, more than 229,000 user prompts, 2 million tool calls from open-source developers. Users "corrected, reported failures, or interrupted agents in 50% of turns"; 59% of agent-produced code made it into user commits; agents authored virtually all committed code in 41% of sessions. — [Baumann et al., arXiv:2604.20779](https://arxiv.org/abs/2604.20779)
- Conflict: search summaries of the earlier version give 6,000 sessions, 44% code survival and 39 to 44% pushback; the figures above are from the v2 abstract. — [arXiv:2604.20779](https://arxiv.org/abs/2604.20779); secondary: [Moonlight review](https://www.themoonlight.io/review/swe-chat-coding-agent-interactions-from-real-users-in-the-wild)
- [study, v1 28 May 2026, v2 31 August 2026] (abstract, summarised) "How Coding Agents Fail Their Users": 20,574 sessions from 1,639 repositories; misalignment is defined as a breakdown made visible through developer pushback; seven forms covering how agents read projects, interpret intent, follow rules, bound their actions, implement and execute code, and report progress. 90.50% of episodes cost effort and trust, not irreversible damage; 91.49% of visible resolutions "still require explicit user correction". Overall rates decline over time while "constraint violations and inaccurate self-reporting grow" as a share, and patterns "persist across adjacent sessions". — [Tang et al., arXiv:2605.29442](https://arxiv.org/abs/2605.29442)
- [study, vendor research] (summarised) Anthropic's failure-signal classifier combines "errors, failed tests, retries, and user pushback"; among sessions that hit trouble, verified success ranged from 4% (novice) to 15% (expert), so the same trouble signal resolves differently by user. — [Anthropic, Claude Code expertise research](https://www.anthropic.com/research/claude-code-expertise)
- [practitioner] (summarised) For rare failures, sample on "a specific tool sequence, unusually long traces, retries"; annotate the first failure because later ones cascade. — [Husain and Shankar, evals FAQ](https://hamel.dev/blog/posts/evals-faq/)
- [vendor blog] (summarised) A near-zero pass rate across many trials "is most often a signal of a broken task, not an incapable agent." — [Anthropic, "Demystifying evals"](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [tool README] Community thresholds for the same signals (edit thrashing 5+, error loop 3+, re-reads 3+, read-to-edit over 10:1 or under 2.0) are listed in section 4; none is validated. — [millionco/claude-doctor](https://github.com/millionco/claude-doctor); [lucemia/claude-session-analyzer](https://github.com/lucemia/claude-session-analyzer)

### Inferences
- A working attribution heuristic assembled from the sources, to be labelled as heuristic in any tool: a failure that is identical across sessions and independent of the task (same command, same error string, same missing binary or path, same permission prompt for a read-only command) points at the environment or harness; a failure that varies with the task and stops after one correction points at the model or the prompt. The "identical across sessions" test is what Factory's cross-session threshold, Devin's "analyze several at once to find shared root causes" advice (round-one search summary) and Docent's missing-package finding have in common.
- Per-tool and per-model baselines are necessary before any count means anything: a rising failure rate after a model switch is not a harness regression. `PostModelSwitch` and the `model` on `SessionStart` make this stratification possible locally.
- Candidate harness-defect signals that the documented Claude Code payloads can detect deterministically: the same `(tool_name, normalised tool_input)` producing the same `PostToolUseFailure.error` two or more times in a session and in two or more sessions; `Notification` of type `permission_prompt` recurring for the same tool pattern; a `PreToolUse` hook block (`tool_decision` with `source` = `hook`) followed by an identical retry; `PostCompact` followed by re-reads of files read before compaction; `InstructionsLoaded` absent for a rule file the task needed; `StopFailure` clusters by `error` type; `Stop` followed within the same session by a failing test command. Each is a prompt for review, not a verdict.
- Pushback is too common to be a defect signal by itself (about half of turns in SWE-chat). What discriminates is repetition of the same correction across sessions, which is also Anthropic's documented trigger for adding a CLAUDE.md line (round one).
- The Tang et al. finding that constraint violations and inaccurate self-reporting are a growing share of failures supports weighting two checks a harness can own: rule-violation detection with a mechanical signature, and "claimed done" versus an independent verification command.

### Gaps
- No study or vendor source was found that validates any signal as discriminating harness defects from model limitations; the attribution heuristic above is my synthesis.
- I read only abstracts of both arXiv studies; per-category rates, annotation method and validation of the pushback classifier are not reported here. SWE-chat's version conflict should be resolved against the paper.
- Nothing was found on reverted edits or re-reading as measured signals (beyond community thresholds), nor on compaction events as a cause of repeated work, nor on test failures after "done" as a quantified signal.

## 6. What do teams say and products do about privacy, secrets, retention and storage of session logs?

### Takeaway
Defaults across products are: transcripts stored locally in plaintext with a finite default retention (Claude Code 30 days), telemetry content redacted unless explicitly enabled, and pattern-based secret redaction applied only when data leaves the machine, described by vendors as best-effort. Claude Code's own documentation states plainly that anything a tool reads, including a `.env` file, lands in the transcript unredacted; a local logging layer that copies hook payloads therefore creates a second unencrypted copy of the same material with its own retention.

### Cited Findings

**Claude Code**
- [vendor doc] (raw) "These files are plaintext. Anything that passes through a tool is written to a transcript on disk: file contents, command output, pasted text." "Transcripts and history are not encrypted at rest. OS file permissions are the only protection. If a tool reads a `.env` file or a command prints a credential, that value is written to `projects/<project>/<session>.jsonl`." — [Claude Code docs, .claude directory](https://code.claude.com/docs/en/claude-directory.md)
- [vendor doc] (raw) Retention: files are deleted once older than `cleanupPeriodDays`; "The default is 30 days and the minimum is 1; setting `0` fails with a validation error." Transcripts of sessions started or last continued in Claude Desktop or Cowork are kept at any age unless `desktopSessionCleanupPeriodDays` is set. `history.jsonl` and `stats-cache.json` are kept until deleted. Auto memory is not swept. The sweep is skipped in `--bare` mode and paused when settings cannot be read. — [.claude directory](https://code.claude.com/docs/en/claude-directory.md)
- [vendor doc] (raw) Mitigations the docs list: lower `cleanupPeriodDays`; `CLAUDE_CODE_SKIP_PROMPT_HISTORY` "to skip writing transcripts and prompt history in any mode"; `--no-session-persistence` with `-p`, or `persistSession: false` in the TypeScript SDK; and permission rules denying reads of credential files. `claude purge <path>` deletes a project's transcripts, auto memory, tasks, debug logs, file history, matching `history.jsonl` lines and its `~/.claude.json` entry after showing a plan; it does not touch the temp-directory scratchpad or pasted images. A `/heapdump` snapshot "contains the full conversation and any credentials the process held, and neither the retention sweep nor the purge touches it." — [.claude directory](https://code.claude.com/docs/en/claude-directory.md)
- [vendor doc] (raw) OpenTelemetry: "OpenTelemetry export to your backend is opt-in"; "By default, raw file contents and code snippets aren't included in metrics or events"; prompt and response text record only lengths unless enabled. `OTEL_LOG_TOOL_DETAILS=1` "can contain the same sensitive content as the session itself, so enable it only when your collector is approved to hold that content." `OTEL_LOG_RAW_API_BODIES` is ignored in project and local settings. Third-party plugin, skill and custom agent names are replaced with `third-party`, `custom_skill`, `custom` unless tool details are enabled. `user.email` is attached when signed in with OAuth and goes only to the configured endpoint. — [Claude Code monitoring docs](https://code.claude.com/docs/en/monitoring-usage.md)
- [vendor doc] (raw) Data sent to Anthropic: `/feedback`, `/bug` and `/share` send conversation history and are "retained for 5 years"; survey-shared transcripts up to 6 months with "Known API key and token patterns" redacted and other content "uploaded as-is"; error reports redact "known patterns of secrets, file paths, email addresses"; operational metrics "never include your code, prompts, or file paths". Opt-outs: `DISABLE_TELEMETRY`, `DISABLE_ERROR_REPORTING`, `DISABLE_FEEDBACK_COMMAND`, `CLAUDE_CODE_DISABLE_FEEDBACK_SURVEY`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`. Consumer accounts that allow training have 5-year retention, otherwise 30 days; commercial accounts 30 days or zero data retention. — [Claude Code docs, Data usage](https://code.claude.com/docs/en/data-usage.md)
- [vendor doc] (raw) Agent SDK stores: "The SDK never deletes from your store on its own. Retention is the adapter's responsibility". Listed reasons for a store include "Compliance and audit. Keep transcripts in storage you already govern, with your own retention rules, encryption, and access controls." — [Agent SDK, session storage](https://code.claude.com/docs/en/agent-sdk/session-storage.md)
- [vendor doc] (raw) Hook hygiene advice: "Skip sensitive files: avoid `.env`, `.git/`, keys, etc."; "Validate and sanitize inputs". — [hooks reference](https://code.claude.com/docs/en/hooks.md)

**Other products**
- [vendor doc] (summarised) Codex: user prompts are redacted from OTel unless `log_user_prompt` is enabled; local history can be disabled or size-capped; analytics and feedback uploads each have a config switch. — [Codex docs, advanced configuration](https://learn.chatgpt.com/docs/config-file/config-advanced)
- [vendor doc] (summarised) Amp stores threads server-side: "Amp Server stores these conversations in its PostgreSQL database in Google Cloud Platform"; deleted thread data is removed within 30 days. "Amp automatically detects and redacts secrets before they can enter threads or be transmitted to any external service", replacing them with a marker such as `[REDACTED:amp]`; covered types include cloud credentials, developer tokens, LLM API keys and generic keys and passwords; described as best-effort that may miss unusual or encoded secrets. "Neither Amp nor our subprocessors train models on your data, unless you have explicitly opted into training." Workspace admins can view private threads with audit logging. — [Amp security](https://ampcode.com/security)
- [vendor doc] (summarised) Cursor hook inputs include `user_email`, full shell output and file contents; the docs' sample audit hook appends the full JSON input to a file under `/tmp`. — [Cursor docs, Hooks](https://cursor.com/docs/agent/hooks)
- [vendor doc] (summarised) Gemini CLI logs prompt text in telemetry by default (`logPrompts` true) once telemetry is enabled; telemetry itself is off by default. — [Gemini CLI docs, telemetry](https://google-gemini.github.io/gemini-cli/docs/cli/telemetry.html)
- [vendor blog] (summarised) Factory's analysis cites sessions only in abstracted form and surfaces a pattern only when it appears "across enough distinct sessions"; the threshold is not published. — [Factory, "Signals"](https://factory.com/news/factory-signals)
- [study, vendor research] (summarised) Anthropic's Clio-based study reports only "aggregates over a minimum number of distinct users." — [Anthropic, Claude Code expertise research](https://www.anthropic.com/research/claude-code-expertise)
- [tool README] (raw) Community practice varies: cctx says "session logs are personal history and shouldn't be committed to git"; code-insights keeps data in a local SQLite file with opt-out anonymous telemetry; agentsview sends anonymous telemetry to PostHog unless disabled; Dhravidk's installer prompt tells the agent not to "import my logs, enable source-text disclosure or start a paid analysis as part of installation." — [jacquardlabs/cctx](https://github.com/jacquardlabs/cctx); [melagiri/code-insights](https://github.com/melagiri/code-insights); [kenn-io/agentsview](https://github.com/kenn-io/agentsview); [Dhravidk/session-analyzer](https://github.com/Dhravidk/session-analyzer)

### Inferences
- A local hook logger that stores `tool_input` and `tool_response` verbatim duplicates the transcript's secret exposure outside Claude Code's retention sweep and outside `claude purge`. The vendor pattern to copy is structural-by-default: record names, sizes, durations, exit classes, hashes of normalised inputs and error first lines; make content capture an explicit opt-in; apply a pattern-based scrub on anything stored; and say in the tool's own output that the scrub is best-effort.
- The log needs its own retention setting, defaulting to no longer than `cleanupPeriodDays`, and its own purge entry in the write manifest, since neither of Claude Code's cleanup paths knows about it. Anything derived from logs and promoted into the repository (a rule, a regression case) should carry only the abstracted evidence, in the way Factory cites "user expressed frustration after third failed tool call" instead of quoting the user.
- Session logs belong outside the repository or in a git-ignored path by default: Amp withdrew public thread sharing because reviewing threads for sensitive snippets did not scale, and a per-user `transcript_path` contains the home directory and project path.
- Sending transcripts to an LLM for analysis is the same data flow as the session itself only if it uses the same provider and account, which is how `/insights` is documented; a tool that routes analysis elsewhere changes the user's data exposure and should say so.
- Since `-p` and SDK runs treat any folder as trusted and run its committed hooks, a logging hook shipped in project settings will run, and write logs, in automation contexts where nobody chose it; the logger should be inert unless explicitly enabled per machine.

### Gaps
- Cursor's privacy and data-governance page could not be read (HTTP 404); Privacy Mode behaviour comes only from forum and third-party snippets and is not reported as fact here. Devin's and Factory's retention and redaction policies were not retrieved.
- Whether Codex rollout files are redacted at rest is not stated in any source read.
- I found no published incident analysis of secrets leaking through coding-agent session logs, and no practitioner write-up of a team retention policy for agent transcripts; guidance here is vendor documentation plus inference.
- Which pattern set Claude Code uses for "known API key and token patterns" is not documented.
