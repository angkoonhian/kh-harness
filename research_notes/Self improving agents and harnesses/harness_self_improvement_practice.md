# Self-improving harnesses for coding agents: industry practice, 2025 to November 2026

Notes compiled 2026-11-18. Every page was read on that date unless stated. Each finding is tagged **[vendor doc]**, **[vendor blog]**, **[practitioner]** or **[study]** so the three kinds of evidence stay separate. Where I only saw a secondary summary of a primary source, the finding says so.

## 1. What do the major vendors ship or recommend?

### Takeaway
Every major vendor now ships two layers: a human-authored, version-controlled instruction file (CLAUDE.md, AGENTS.md, rules) and an agent-authored memory store that is machine- or service-local, and every vendor that documents both tells users to keep binding rules in the first and treat the second as recall only. The only shipped features that close a full loop with measured promotion and demotion of learned rules are Cursor Bugbot's learned rules and GitHub Copilot Memory; Devin proposes knowledge but always waits for a human.

### Cited Findings

**Claude Code (Anthropic)**
- [vendor doc] Two memory systems are loaded at the start of every conversation: CLAUDE.md ("instructions you write") and auto memory ("notes Claude writes itself based on your corrections and preferences"). "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead." — [Claude Code docs, "How Claude remembers your project"](https://code.claude.com/docs/en/memory)
- [vendor doc] The documented triggers for adding to CLAUDE.md are: "Claude makes the same mistake a second time"; "A code review catches something Claude should have known about this codebase"; "You type the same correction or clarification into chat that you typed last session"; "A new teammate would need the same context to be productive". — [Claude Code docs, memory](https://code.claude.com/docs/en/memory)
- [vendor doc] Routing rule: keep CLAUDE.md to "facts Claude should hold in every session"; "If an entry is a multi-step procedure or only matters for one part of the codebase, move it to a skill or a path-scoped rule instead." — [Claude Code docs, memory](https://code.claude.com/docs/en/memory)
- [vendor doc] Auto memory saves four typed kinds of note, recorded as a `type` frontmatter field: `user`, `feedback` ("corrections you give Claude and approaches you confirm"), `project`, `reference`. "Claude skips anything it can derive from the codebase, such as architecture, file paths, or debugging fixes. It also skips anything your CLAUDE.md files already say." It "doesn't save something every session". — [Claude Code docs, memory](https://code.claude.com/docs/en/memory)
- [vendor doc] Auto memory is on by default in local sessions, stored at `~/.claude/projects/<project>/memory/` with a `MEMORY.md` index plus one topic file per memory; it is machine-local, shared across worktrees of one repository, and not shared across machines. Disable with `autoMemoryEnabled: false` or `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`. — [Claude Code docs, memory](https://code.claude.com/docs/en/memory)
- [vendor doc] Claude Code stamps a `modified` ISO 8601 timestamp in the frontmatter of each memory file on write, "to show how current the fact is, both to you and to Claude when it reads the memory back." — [Claude Code docs, memory](https://code.claude.com/docs/en/memory)
- [vendor doc] The main conversation's auto memory is not loaded into subagents (a fork is the exception); a subagent can have its own separate memory directory through the subagent `memory` field. — [Claude Code docs, memory](https://code.claude.com/docs/en/memory)
- [vendor doc] "When you ask Claude to remember something ... Claude saves it to auto memory. To add instructions to CLAUDE.md instead, ask Claude directly." — [Claude Code docs, memory](https://code.claude.com/docs/en/memory)
- [vendor doc] `/doctor prompt-audit` (Claude Code v2.1.283 or later) checks CLAUDE.md, CLAUDE.local.md, AGENTS.md, rules, skills, commands, subagents and output styles for "instructions written for older models, references to files or commands that don't exist, and files that contradict each other", and reports proposed edits without changing files until asked. — [Claude Code docs, memory](https://code.claude.com/docs/en/memory)
- [vendor doc] Claude Code reads a repository's AGENTS.md directly (v2.1.277 or later) when there is no CLAUDE.md in the working directory or above it. — [Claude Code docs, memory](https://code.claude.com/docs/en/memory)
- [vendor doc] With `CLAUDE_CODE_NEW_INIT=1`, `/init` asks which artifacts to set up (CLAUDE.md files, skills, hooks), explores with a subagent and "presents a reviewable proposal before writing any files". — [Claude Code docs, memory](https://code.claude.com/docs/en/memory)
- [practitioner, third-party only] `/insights` analyses local session history (reported as the last 30 days, up to 50 sessions) and produces an HTML report with friction points and suggested CLAUDE.md additions for instructions repeated across sessions; some guides say it also suggests skills and hooks. One guide warns the suggestions are "pattern-matched from repetition, not judgement". I found no official Anthropic page for this in my searches; details come from third-party guides such as [SSW Rules](https://www.ssw.com.au/rules/use-claude-insights) and [angelo-lima.fr](https://angelo-lima.fr/en/claude-code-insights-command/).
- [vendor blog, seen only through search summary] Anthropic's "Effective harnesses for long-running agents" recommends a progress file kept alongside git history so a fresh context window can recover state, with an initializer agent followed by coding agents. — [Anthropic Engineering](https://anthropic.com/engineering/effective-harnesses-for-long-running-agents)

**OpenAI Codex**
- [vendor doc] Codex memories: "Codex can turn useful context from eligible prior chats into local memory files." Generation runs in the background after a chat "has been idle long enough to avoid summarizing work that's still in progress"; active or short-lived sessions are skipped. "Local Codex memories are off by default." Stored under `~/.codex` (`memories_v2/` for fresh profiles). — [OpenAI Codex docs, Memories](https://learn.chatgpt.com/docs/customization/memories?surface=app) (redirect target of developers.openai.com/codex/memories)
- [vendor doc] "Keep required team guidance in `AGENTS.md` or checked-in documentation." "Treat memories as a helpful recall layer, not as the only source for rules that must always apply." The files are "generated state", not the primary control surface. — [OpenAI Codex docs, Memories](https://learn.chatgpt.com/docs/customization/memories?surface=app)
- [vendor doc] Controls: `memories.generate_memories`, `memories.use_memories`, `memories.disable_on_external_context` (keeps chats that used MCP, web search or tool search out of generation), `memories.consolidation_model`, `memories.min_rate_limit_remaining_percent`. Secrets are redacted from generated fields. No automatic expiry is documented; the only forgetting mechanism is a full reset. — [OpenAI Codex docs, Memories](https://learn.chatgpt.com/docs/customization/memories?surface=app)
- [vendor blog, via secondary summaries; openai.com returned HTTP 403 to my fetch] OpenAI's harness engineering post describes its own team's loop in detail; see section 2. — [OpenAI, "Harness engineering: leveraging Codex in an agent-first world"](https://openai.com/index/harness-engineering/)

**Cursor**
- [vendor doc] Four rule sources: Project Rules (`.cursor/rules`), User Rules, Team Rules, AGENTS.md. Project rule modes: Always Apply, Apply Intelligently (by description), Apply to Specific Files (globs), Apply Manually. `/create-rule` in Agent writes a rule file. — [Cursor docs, Rules](https://cursor.com/docs/context/rules)
- [vendor doc] "Start simple. Add rules only when you notice Agent making the same mistake repeatedly." "Keep rules under 500 lines." Avoid copying full style guides ("use a linter"). The page does not document a Memories feature. — [Cursor docs, Rules](https://cursor.com/docs/context/rules)
- [vendor blog, 8 April 2026] Bugbot learned rules: Bugbot learns from three signals on merged PRs: reactions to its comments (a downvote means not useful), replies to its comments, and human reviewer comments that flag issues it missed. Signals become **candidate** rules that are evaluated against incoming PRs; with accumulated signal a candidate is promoted to **active**; "If an active rule consistently generates negative signal, Bugbot can disable it." Users can edit or delete rules, and can run a backfill over recent PRs. No promotion threshold is published. — [Cursor blog, "Bugbot learning"](https://cursor.com/blog/bugbot-learning)
- [vendor blog, 8 April 2026] Reported scale: more than 110,000 repos enabled learning, producing more than 44,000 learned rules. Resolution rate (share of flagged bugs fixed by merge time) rose from 52% at the July 2025 launch to 78.13% across 50,310 PRs, measured by an LLM judge on public repositories only. — [Cursor blog, "Bugbot learning"](https://cursor.com/blog/bugbot-learning)
- [practitioner, forum] Learned rules live in Cursor's dashboard, not in the repository; a forum feature request asks for a Git-based workflow that proposes them as pull requests. — [Cursor forum](https://forum.cursor.com/t/api-or-git-based-workflow-to-promote-bugbot-learned-rules-into-repository-rules/171018)

**GitHub Copilot**
- [vendor blog, 15 January 2026, updated 12 November 2026] Agents create memories through a `store_memory` tool call when they find something "likely to have actionable implications for future tasks". Each memory has a subject, a fact, citations (code locations) and a reason. Instead of offline curation, the agent verifies the cited locations against the current branch just before using a memory; if the code contradicts it, the agent stores a corrected version; if it holds, the agent stores it again to refresh its timestamp. — [GitHub blog, "Building an agentic memory system for GitHub Copilot"](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)
- [vendor blog] Measured results: coding agent PR merge rate 83% without memories versus 90% with; code review positive feedback 75% versus 77%; both A/B results reported at p < 0.00001. Code review precision +3% and recall +4% on evaluation PRs. In an adversarial test, repositories were seeded with memories contradicting the code; agents verified citations, found the contradictions and updated the memories. — [GitHub blog](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)
- [vendor doc] Copilot Memory is on all paid plans. Repository-level facts are shared with collaborators; user-level preferences follow the user. Copilot "checks the fact's citations against the current branch" and uses an internal voting system (upvote validated memories, downvote wrong or outdated ones). Default expiry is 90 days; enterprise and organization owners can set repository fact expiry from 7 to 180 days. Repository facts can be viewed and deleted in repository settings by users with write access. — [GitHub docs, Copilot Memory](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)
- Conflict: several secondary sources give a 28-day expiry (consistent with the January 2026 public preview); the current docs say 90 days by default. — [GitHub changelog, 15 January 2026](https://github.blog/changelog/2026-01-15-agentic-memory-for-github-copilot-is-in-public-preview/); [GitHub docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)

**Devin (Cognition)**
- [vendor doc, via search summary] Devin suggests Knowledge from feedback in chat; the user can edit, dismiss or regenerate a suggestion before saving. Playbooks are for step-by-step procedures; Knowledge is for general tips and conventions. — [Devin docs](https://docs.devin.ai/work-with-devin/advanced-capabilities)
- [vendor doc] Scheduled knowledge maintenance: "knowledge suggestions accumulate from every session." A weekly scheduled session triages pending suggestions, merges entries on the same topic, resolves contradictory entries "based on recency", and flags "entries referencing old file paths, deprecated APIs, or removed packages". Triage criteria: new and useful, propose an entry "with a specific trigger description"; overlapping, propose a merge; "outdated or too vague", propose dismissal. "Devin does not automatically apply knowledge changes." "When in doubt, keep the entry and flag it for review rather than proposing removal." — [Devin docs, scheduled knowledge maintenance](https://docs.devin.ai/use-cases/gallery/scheduled-knowledge-maintenance.md)

**Windsurf**
- [vendor doc, via search summary] Cascade auto-generates memories, stored locally in `~/.codeium/windsurf/memories/` and tied to the workspace. The docs say: "For knowledge you want Cascade to reliably reuse, write it as a Rule or add it to AGENTS.md in your repo rather than relying on auto-generated Memories." — [Windsurf/Devin docs, Memories & Rules](https://docs.devin.ai/desktop/cascade/memories)

**Factory (Droid)**
- [vendor doc] The documented persistence mechanism is AGENTS.md, in git "so every teammate and automation session gets the same operating context." Skills hold "Reusable workflows, checklists, or domain expertise that should load only when relevant." "Do not paste long run books into `AGENTS.md`." Caps: 80,000 characters at initial load, 40,000 per tool call; "These are caps, not targets." The page documents no cross-session learned memory. — [Factory docs, memory management](https://docs.factory.com/guides/power-user/memory-management)
- [vendor doc, via search summary] "Agent Readiness" scores whether a repository has the structure, validation and operational signals for autonomous agents. — [Factory docs, Agent Readiness](https://docs.factory.ai/agent-readiness/overview)

**Gemini CLI and Jules (Google)**
- [vendor doc, via search summary] Gemini CLI's `save_memory` tool appends facts under a "Gemini Added Memories" heading in the user's home GEMINI.md, which is loaded in later sessions. — [Gemini CLI docs, Memory Tool](https://google-gemini.github.io/gemini-cli/docs/tools/memory.html)
- [vendor doc, via search summary] Jules has a per-repository memory that saves "preferences, nudges, and corrections" during tasks, toggled under a Knowledge setting, and reads AGENTS.md. — [Jules changelog](https://jules.google/docs/changelog/)

**Amp (Sourcegraph)**
- [vendor doc, via search summary] Amp reads AGENTS.md "for guidance on codebase structure, build/test commands, and conventions". Files in the working directory and its parents load automatically; subtree files load only when the agent reads a file in that subtree; `$HOME/.config/amp/AGENTS.md` and `$HOME/.config/AGENTS.md` always load. Amp offers to generate an AGENTS.md when none exists, and the user can ask Amp to update the file from a thread. `agents-md list` shows what loaded. — [Amp docs, AGENTS.md](https://ampcode.com/docs/customize/agents-md)
- [third-party] No built-in cross-session memory store was found in Amp's documentation; a third-party blog says the docs list AGENTS.md, skills and plugins as the customisation surfaces, and third-party plugins add memory. — [memorylake.ai](https://www.memorylake.ai/en/blogs/migrate-claude-code-to-amp); [Nowledge Mem integration](https://mem.nowledge.co/docs/integrations/amp)

### Inferences
- The vendor consensus is a two-tier split: binding rules are human-reviewed and version-controlled; agent-written memory is advisory. A plugin that writes learnings straight into a repository's rule registry would be doing something no vendor does without a review gate (Devin: human approval; Bugbot: candidate state plus signal; Copilot: citation check at read time).
- Three distinct validity mechanisms exist for learned items: human approval before activation (Devin, Claude Code `/init` proposals, `/doctor prompt-audit`), statistical promotion and demotion from outcome signal (Bugbot), and read-time verification against code citations plus expiry (Copilot). They are complementary, and only the second and third come with published outcome numbers.
- Claude Code's documented routing (every-session fact in CLAUDE.md; procedure in a skill; part-of-codebase in a path-scoped rule; must-happen in a hook) is the nearest thing to an official decision table for where a learning goes.

### Gaps
- Amp (Sourcegraph): the absence of a built-in memory feature rests on search summaries and a third-party blog, not on a full read of Amp's manual.
- Cursor "Memories" (the 2025 feature): the current rules page does not mention it, and I did not find an official page stating whether it was removed or folded into rules. A third-party course page still describes it.
- Claude Code `/insights`: no official documentation found; all details are third-party.
- I did not read Claude Code's skills, hooks or plugins reference pages in this pass, so nothing here covers documented skill-creation or hook details beyond what the memory page says.
- Vendor-reported numbers (Bugbot 52% to 78%, Copilot 83% to 90%) are self-measured; I found no independent replication.

## 2. What is "harness engineering", who popularised it, and what do the write-ups say about feeding failures back?

### Takeaway
The term was popularised in February 2026 by three near-simultaneous sources: Mitchell Hashimoto (5 February), OpenAI's Ryan Lopopolo (11 February) and Birgitta Böckeler (memo 17 February, full article 2 April). All three describe the same loop: when an agent's mistake repeats, change the environment (a doc line, a tool, a lint, a structural test) so it cannot recur, and prefer mechanical enforcement when documentation is not enough. Every's "compound engineering" is the same loop packaged as a workflow step.

### Cited Findings
- [practitioner, 5 February 2026] Hashimoto's step 5, "Engineer the Harness": "anytime you find an agent makes a mistake, you take the time to engineer a solution such that the agent never makes that mistake again." He says he borrowed the term. Two forms: (1) "better implicit prompting", updating AGENTS.md for simple problems such as wrong commands or wrong APIs; of Ghostty's file he says "Each line in that file is based on a bad agent behavior, and it almost completely resolved them all." (2) "Actual, programmed tools" such as scripts to take screenshots or run filtered tests, usually paired with an AGENTS.md change so the agent knows the tool exists. — [Mitchell Hashimoto, "My AI Adoption Journey"](https://mitchellh.com/writing/my-ai-adoption-journey)
- [vendor blog, 11 February 2026, read via secondary summary; primary returned 403] OpenAI's team reports roughly a million lines of code and about 1,500 PRs over five months with no hand-written code, by a team that grew to seven engineers, about 3.5 PRs per engineer per day. — [OpenAI, "Harness engineering"](https://openai.com/index/harness-engineering/); figures as summarised at [AI-Wiki source note](https://businessdatasolutions.github.io/ai-wiki/sources/2026-02-11-lopopolo-codex-harness-engineering)
- [vendor blog, via the same secondary summary] The team dropped one large AGENTS.md in favour of a roughly 100-line file used as a table of contents pointing into a structured `docs/` directory. Reasons quoted for the failure of the large file: "Too much guidance becomes non-guidance."; "It rots instantly."; "It's hard to verify." Also quoted: "From the agent's point of view, anything it can't access in-context while running effectively doesn't exist." — [AI-Wiki source note on the OpenAI post](https://businessdatasolutions.github.io/ai-wiki/sources/2026-02-11-lopopolo-codex-harness-engineering); original at [OpenAI](https://openai.com/index/harness-engineering/)
- [vendor blog, via the same secondary summary] On feedback: "Human taste is fed back into the system continuously." "When documentation falls short, we promote the rule into code." Review comments, refactoring PRs and user-facing bugs become documentation updates or tooling rules; Codex-written custom linters enforce layer boundaries. — [AI-Wiki source note](https://businessdatasolutions.github.io/ai-wiki/sources/2026-02-11-lopopolo-codex-harness-engineering)
- [vendor blog, via the same secondary summary] On entropy: the team first spent "every Friday (20% of the week)" cleaning up "AI slop", which did not scale. It replaced that with "golden principles" encoded in the repository (example: "prefer shared utility packages over hand-rolled helpers") and recurring background Codex tasks that find deviations and open small refactoring PRs, most auto-merged. A "doc-gardening" agent scans for stale documentation and opens fix-up PRs. Quality grades are tracked per area. — [AI-Wiki source note](https://businessdatasolutions.github.io/ai-wiki/sources/2026-02-11-lopopolo-codex-harness-engineering)
- [practitioner, 2 April 2026] Böckeler defines the harness broadly as "everything in an AI agent except the model itself" and narrows to the user's "outer harness". Guides (feedforward) "anticipate the agent's behaviour and aim to steer it before it acts"; sensors (feedback) "observe after the agent acts and help it self-correct". Controls are computational ("deterministic and fast, run by the CPU": tests, linters, type checkers) or inferential (AI review, LLM as judge; "more non-deterministic"). Feedback-only yields "an agent that keeps repeating the same mistakes". — [Birgitta Böckeler, "Harness engineering for coding agent users", martinfowler.com](https://martinfowler.com/articles/harness-engineering.html)
- [practitioner] The steering loop: "The human's job in this is to steer the agent by iterating on the harness." "Whenever an issue happens multiple times, the feedforward and feedback controls should be improved." Agents can help: "Agents can help write structural tests, generate draft rules from observed patterns, scaffold custom linters." — [Böckeler, martinfowler.com](https://martinfowler.com/articles/harness-engineering.html)
- [practitioner] Böckeler's open questions: "How do we keep a harness coherent as it grows, with guides and sensors in sync, not contradicting each other?"; "If sensors never fire, is that a sign of high quality or inadequate detection mechanisms?"; "We need a way to evaluate harness coverage and quality similar to what code coverage and mutation testing do." She gives no explicit rule for choosing a guide versus a sensor. — [Böckeler, martinfowler.com](https://martinfowler.com/articles/harness-engineering.html)
- [practitioner] "Harnessability": "Not every codebase is equally amenable to harnessing"; strong typing, clear module boundaries and opinionated frameworks make controls easier. She also proposes "harness templates", "a bundle of guides and sensors that leash a coding agent to the structure, conventions and tech stack" of a service topology. — [Böckeler, martinfowler.com](https://martinfowler.com/articles/harness-engineering.html)
- [practitioner, undated guide by Kieran Klaassen and Trevin Chow] Compound engineering: "each unit of engineering work should make subsequent units easier—not harder." Loop: Plan, Work, Review, Compound, Repeat. The compound step: capture the solution (what worked, what did not, the reusable insight), make it findable (YAML frontmatter with tags and categories), update the system (add patterns to CLAUDE.md, create new agents "when warranted"), and verify with the question "Would the system catch this automatically next time?" — [Every, "Compound Engineering" guide](https://every.to/guides/compound-engineering)
- [practitioner] The plugin's `/workflows:compound` command spawns six parallel subagents (context analyzer, solution extractor, related docs finder, prevention strategist, category classifier, documentation writer) and writes a searchable markdown file into a categorised `docs/solutions/`. The guide suggests plan and review take about 80% of time, and separately a "50/50 rule" between features and system improvement. — [Every guide](https://every.to/guides/compound-engineering)
- [practitioner] Every's claims of benefit are experiential, not measured: for example an hour building a review agent "saves 10 hours of review over the next year". The guide gives no guidance on pruning or deprecating captured learnings. — [Every guide](https://every.to/guides/compound-engineering)
- [practitioner, via third-party summaries only] Geoffrey Huntley's "Ralph" loop (an agent run repeatedly on the same prompt) is tuned the same way: start with no guardrails, and each time the loop fails add a one-line "sign" to the prompt so the next iteration sees it; summaries quote his playground metaphor, with the sign reading "SLIDE DOWN, DON'T JUMP". The wording was not confirmed on ghuntley.com. — [Codesota explainer](https://www.codesota.com/explainers/ralph-loop); [awesomeclaude.ai](https://awesomeclaude.ai/ralph-wiggum); background in [HumanLayer, "A Brief History of Ralph"](https://humanlayer.dev/blog/brief-history-of-ralph)
- [practitioner, 23 February 2026, via search summary] Simon Willison's "Agentic Engineering Patterns" guide defines a coding agent as a harness around an LLM and includes a chapter on hoarding reusable prompts, working examples and documented patterns for agents to recombine. I found no Willison post that sets out a failure-to-harness loop of its own. — [Simon Willison, Agentic Engineering Patterns](https://simonwillison.net/guides/agentic-engineering-patterns/)
- [study, 16 February 2026, revised 30 June 2026] An academic paper has adopted the name: "Harness Engineering for Agentic AI Coding Tools: An Exploratory Study" (Galster, Mohsenimofidi, Lulla, Abubakar, Treude, Baltes) identifies eight configuration mechanisms across Claude Code, Copilot, Cursor, Gemini and Codex in 2,853 GitHub repositories. "Context Files dominate the configuration landscape and are often the sole mechanism in a repository"; "few repositories adopt advanced mechanisms such as Skills and Subagents"; "Skills predominantly rely on static instructions rather than executable scripts." — [arXiv:2602.14690](https://arxiv.org/abs/2602.14690)

### Inferences
- None of the three founding write-ups names a single coiner. Hashimoto says he borrowed the term, and Böckeler's article says only that the term "first appeared" around her February memo, so "popularised in February 2026 by Hashimoto, OpenAI and Böckeler" is the defensible wording; "coined by" is not supported.
- The escalation order implied by all three is: a line of documentation first (cheap, fast, unreliable), then a tool or script the doc points to, then a mechanical check (lint, structural test, hook) once the doc has demonstrably failed. OpenAI states the promotion rule outright; Hashimoto's two forms and Böckeler's guide/sensor pairing imply it.
- Böckeler's open question about sensors that never fire maps directly onto a rules registry with named enforcers: an enforcer with zero recorded firings is either a solved problem or a dead check, and the registry cannot tell which without a deliberate probe (the mutation-testing analogy she draws).
- The Every compound step's test question ("Would the system catch this automatically next time?") is a usable acceptance criterion for a captured learning: a learning that changes nothing the system will consult or enforce has not compounded.

### Gaps
- I could not fetch the OpenAI post itself (HTTP 403). All quotations from it come through one secondary summary page and should be checked against the original before being quoted in a report. One claim often attributed to the post, that custom lint error messages carry remediation instructions for the agent, was absent from the summary I read and is unverified.
- Geoffrey Huntley's and Simon Willison's own pages were not read; both entries above rest on search summaries of secondary coverage and should not be quoted as primary.
- I found no measured, controlled evidence that the harness-engineering loop itself (as opposed to its components) improves outcomes; the founding sources are experience reports from teams with strong incentives and unusual greenfield conditions.

## 3. What mechanisms capture learnings, and what decides told rule versus mechanical enforcer?

### Takeaway
Capture mechanisms in production fall into five families: in-session agent tool calls, background transcript summarisation, review-comment and reaction mining, explicit end-of-work reflection steps, and usage-report mining. The published decision rule for told versus enforced is consistent across sources: tell first when the mistake is simple and cheap to describe; enforce mechanically when the instruction must hold every time, when a deterministic tool can check it, or when the told rule has already failed.

### Cited Findings

**Capture mechanisms**
- [vendor blog] In-session tool call at the moment of discovery: Copilot agents call `store_memory` with subject, fact, citations and reason. — [GitHub blog](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)
- [vendor doc] In-session writes from corrections: Claude Code auto memory records `feedback` notes for "corrections you give Claude and approaches you confirm", and the UI shows "Saved 2 memories" / "Recalled 2 memories". — [Claude Code docs](https://code.claude.com/docs/en/memory)
- [vendor doc] Background transcript summarisation after idle: Codex generates memories from eligible prior chats in the background, skipping active or short-lived sessions, and can exclude chats that used external context. — [OpenAI Codex docs](https://learn.chatgpt.com/docs/customization/memories?surface=app)
- [vendor blog] PR review mining: Bugbot uses reactions, replies and human reviewer comments on merged PRs, including issues it missed, to draft candidate rules, and supports a backfill over recent PRs. — [Cursor blog](https://cursor.com/blog/bugbot-learning)
- [vendor doc] Suggestion queue plus scheduled curation: Devin accumulates knowledge suggestions from every session and a weekly session triages them for human approval. — [Devin docs](https://docs.devin.ai/use-cases/gallery/scheduled-knowledge-maintenance.md)
- [practitioner] Explicit end-of-work reflection: Every's compound step runs after review, with parallel subagents writing a categorised solution document and updating CLAUDE.md. — [Every guide](https://every.to/guides/compound-engineering)
- [practitioner, third-party] Retrospective usage mining: Claude Code `/insights` reads local session history and proposes CLAUDE.md additions for instructions repeated across sessions. — [SSW Rules](https://www.ssw.com.au/rules/use-claude-insights)
- [vendor blog, via secondary summary] Review comments, refactoring PRs and user-facing bugs are converted into documentation updates or tooling rules; background agents open cleanup and doc-fix PRs. — [AI-Wiki note on the OpenAI post](https://businessdatasolutions.github.io/ai-wiki/sources/2026-02-11-lopopolo-codex-harness-engineering)
- [practitioner] Agents themselves can draft the enforcers: "Agents can help write structural tests, generate draft rules from observed patterns, scaffold custom linters." — [Böckeler](https://martinfowler.com/articles/harness-engineering.html)

**Told versus enforced**
- [vendor doc] "If the instruction is something that must run at a specific point, such as before every commit or after each file edit, write it as a hook instead. Hooks execute as shell commands at fixed lifecycle events and apply regardless of what Claude decides to do." — [Claude Code docs](https://code.claude.com/docs/en/memory)
- [vendor doc] "To block an action regardless of what Claude decides, use a PreToolUse hook instead." — [Claude Code docs](https://code.claude.com/docs/en/memory)
- [vendor blog, via secondary summary] "When documentation falls short, we promote the rule into code." — [AI-Wiki note on the OpenAI post](https://businessdatasolutions.github.io/ai-wiki/sources/2026-02-11-lopopolo-codex-harness-engineering)
- [practitioner, 25 November 2025] "Never send an LLM to do a linter's job." HumanLayer recommends a `Stop` hook "that runs your formatter & linter and presents errors to Claude for it to fix" and says "Don't make Claude find the formatting issues itself." — [HumanLayer, "Writing a good CLAUDE.md"](https://www.humanlayer.dev/blog/writing-a-good-claude-md)
- [vendor doc] Cursor advises against copying full style guides into rules ("use a linter"). — [Cursor docs](https://cursor.com/docs/context/rules)
- [practitioner] Hashimoto: AGENTS.md for simple problems (wrong commands, wrong APIs); programmed tools when the agent needs a capability or a check, and "fast, high quality tools to automatically tell it when it is wrong." — [Hashimoto](https://mitchellh.com/writing/my-ai-adoption-journey)
- [practitioner] Placement of sensors by cost: "You want to have checks as far left in the path to production as possible", with cheap fast controls early and expensive ones (such as mutation testing) after integration. — [Böckeler](https://martinfowler.com/articles/harness-engineering.html)
- [vendor doc] The repeat threshold for adding even a told rule is two occurrences: "Claude makes the same mistake a second time" (Claude Code); "only when you notice Agent making the same mistake repeatedly" (Cursor); "Whenever an issue happens multiple times" (Böckeler). — [Claude Code docs](https://code.claude.com/docs/en/memory); [Cursor docs](https://cursor.com/docs/context/rules); [Böckeler](https://martinfowler.com/articles/harness-engineering.html)
- [vendor doc] What not to capture: Claude Code auto memory "skips anything it can derive from the codebase" and "anything your CLAUDE.md files already say". — [Claude Code docs](https://code.claude.com/docs/en/memory)

### Inferences
- A workable decision procedure assembled from the sources: (1) is it derivable from the code or already stated? Then capture nothing. (2) Has it happened at least twice, or did a reviewer catch it? Then it qualifies. (3) Can a deterministic tool check it? Then make it an enforcer (lint, test, hook) and add at most a one-line pointer for the agent. (4) Must it happen at a fixed lifecycle point? Then a hook. (5) Is it a procedure or scoped to part of the codebase? Then a skill or path-scoped rule. (6) Otherwise a short told rule, flagged for promotion if it is violated again.
- The strongest capture signals in shipped products are corrections tied to an outcome (a downvote, a reviewer comment on a merged PR, a user correction), not free-form self-reflection by the agent. Bugbot and Copilot, the two with numbers, both anchor learnings to observable evidence (PR signal, code citations).
- No vendor documents automatic conversion of a learning into a mechanical enforcer without a human in the loop. The OpenAI team has agents write the linters, but the decision to promote is described as the team's.

### Gaps
- No source gives a quantitative threshold for promotion from told to enforced (for example a violation count), and Cursor does not publish Bugbot's candidate-to-active criteria.
- CI failure mining as a distinct, productised capture mechanism: I found no vendor feature or write-up in this pass that mines CI failures into rules, beyond the general "sensor fires repeatedly, add a guide" advice.
- Automatic correction detection in transcripts (classifying a user turn as a correction): Claude Code documents the outcome (`feedback` memories) but not the detection method.

## 4. What evidence exists on whether instruction files and learned rules help?

### Takeaway
The measured evidence is unfavourable to large or auto-generated instruction files and favourable to small, evidence-anchored, verified learnings. The best controlled study (ETH Zurich, February 2026) found no significant success-rate gain from context files and about 20% higher cost, with LLM-generated files slightly negative; a May 2026 factorial study found file size and position did not detectably change compliance but compliance decayed within a session; and SkillsBench found curated skills help while self-generated skills do not.

### Cited Findings
- [study, February 2026; v3 dated 29 September 2026] "Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?" (Gloaguen, Mündler-Sasahara, Müller, Raychev, Vechev; ETH Zurich and LogicStar.ai). Method: SWE-bench Lite (300 tasks, 11 Python repositories, no developer context files) plus a new benchmark of 138 instances from 12 Python repositories with developer-committed context files; agents Claude Code (Sonnet 4.5), Codex (GPT-5.2, GPT-5.1 mini), Qwen Code (Qwen3-30B-coder); three settings: no file, LLM-generated via each agent's init command, developer-written. — [arXiv:2602.11988](https://arxiv.org/html/2602.11988)
- [study] Results: LLM-generated versus none, -0.5 points on SWE-bench Lite (p = 0.87) and -2 points on the new benchmark (p = 0.37); developer-written versus none, +2.4 points (p = 0.21); developer-written versus LLM-generated significant at p = 0.038. LLM files added about 2.45 and 3.92 steps and about 20% and 23% cost; developer files added about 3.34 steps and up to 19% cost. Developer files improved every agent except Claude Code. — [arXiv:2602.11988](https://arxiv.org/html/2602.11988)
- [study] Agents do follow the files: when a tool was mentioned, use rose sharply (uv: 1.6 uses per instance when mentioned versus under 0.01 when not; repository-specific tools 2.5 versus under 0.05). Repository overviews did not help agents find relevant files sooner. When all other documentation was removed, LLM-generated files improved performance by 2.7% on average, so the authors conclude they mostly duplicate existing docs. Reasoning tokens rose 14 to 22% for GPT-5.2 with LLM files. Recommendation: omit LLM-generated context files for now; human-written files should contain only what is not already documented, such as specific conventions or tooling requirements. — [arXiv:2602.11988](https://arxiv.org/html/2602.11988)
- Naming conflict: the v3 HTML I read calls the new benchmark "CTXbench"; search summaries of earlier versions and the ICLR 2026 listing call it "AGENTbench", and one summary cites an "average increase of 4%" for developer files where v3 gives +2.4 points. The numbers above are from v3. — [arXiv:2602.11988 v3](https://arxiv.org/html/2602.11988); [ICLR 2026 listing](https://iclr.cc/virtual/2026/10021235)
- [study, 11 May 2026] "Instruction Adherence in Coding Agent Configuration Files: A Factorial Study of Four File-Structure Variables" (Damon McMillan). Method: 1,650 Claude Code CLI sessions, 16,050 function-level observations, two TypeScript codebases, three models, five tasks; compliance with a trivial target annotation; manipulated file size, instruction position, file architecture (single versus split) and contradictions in adjacent files. Result: none of the four variables or their two-way interactions produced a detectable difference after correction; the size and conflict nulls have Bayes factors of 0.05 to 0.10 (support for no effect). The largest effect was within-session drift: each additional function generated was associated with about 5.6% lower odds of compliance (OR = 0.944), non-monotonic, replicated on a second codebase and on Opus 4.6, and found during analysis, not pre-specified. — [arXiv:2605.10039](https://arxiv.org/abs/2605.10039)
- [study, 15 July 2025; NeurIPS 2025] "How Many Instructions Can LLMs Follow at Once?" (Jaroslawicz, Whiting, Shah, Maamari; Distyl AI). IFScale: up to 500 keyword-inclusion instructions in a report-writing task, 20 models from seven providers. "Even the best frontier models only achieve 68% accuracy at the max density of 500 instructions"; the paper reports three degradation patterns and a bias towards earlier instructions. — [arXiv:2507.11538](https://arxiv.org/abs/2507.11538)
- [practitioner, 25 November 2025] HumanLayer derives from that paper the heuristic that "Frontier thinking LLMs can follow ~ 150-200 instructions with reasonable consistency" and adds that "Claude Code's system prompt contains ~50 individual instructions"; the author notes the question "hasn't been investigated in an incredibly rigorous manner". The 150 to 200 figure is the blog's reading, not a number the paper's abstract states. — [HumanLayer](https://www.humanlayer.dev/blog/writing-a-good-claude-md)
- [practitioner] HumanLayer reports that Claude Code wraps CLAUDE.md with a reminder that the context "may or may not be relevant to your tasks", and argues that the more non-universal content a file has, the more likely the whole file is ignored. — [HumanLayer](https://www.humanlayer.dev/blog/writing-a-good-claude-md)
- [vendor doc] Anthropic's own statement on adherence: "Longer files consume more context and reduce adherence"; "there's no guarantee of strict compliance, especially for vague or conflicting instructions"; CLAUDE.md "is delivered as a user message after the system prompt, not as part of the system prompt itself"; "if two instructions contradict each other, Claude may pick one arbitrarily." — [Claude Code docs](https://code.claude.com/docs/en/memory)
- [study, July 2025] Chroma's "Context Rot" report (Hong, Troynikov, Huber): 18 models including GPT-4.1, Claude 4 and Gemini 2.5; performance becomes less reliable as input length grows, and semantically similar distractors hurt more at longer lengths. Chroma sells a retrieval database, which is a stated interest. — [Chroma Research](https://trychroma.com/research/context-rot)
- [study, February 2026] SkillsBench (arXiv:2602.12670; 7 agent-model configurations, 7,308 trajectories, three conditions: no skills, curated skills, self-generated skills). Curated skills raised average pass rate by 16.2 points, ranging from +4.5 for software engineering to +51.9 for healthcare, with 16 of 84 tasks negative. Self-generated skills gave no average benefit (reported as about -1.3 points). Focused skills with 2 to 3 modules beat comprehensive documentation. — [arXiv:2602.12670](https://arxiv.org/html/2602.12670v1)
- [study, 17 November 2025] "Agent READMEs" (Chatlatanagulchai et al.): 2,303 context files from 1,925 repositories (922 CLAUDE.md, 694 AGENTS.md, 687 Copilot instructions). Median length 485 words (Claude Code), 335.5 (Codex), 535 (Copilot); 67.4% of CLAUDE.md files were modified in multiple commits. "Manifest evolution is driven by small, incremental additions, while deletions are minimal" (median deletions under 15 words; Claude Code median addition 57 words per commit). In 332 classified CLAUDE.md files: Testing 75.0%, Implementation Details 69.9%, Architecture 67.7%, Build and Run 62.3%, Security 14.5%, Performance 14.5%. The authors name "context debt" as a form of technical debt. — [arXiv:2511.12884](https://arxiv.org/html/2511.12884v1)
- [vendor blog, self-measured] Positive evidence for learned, verified memories: Copilot PR merge rate 83% to 90% and review positive feedback 75% to 77% in A/B tests (p < 0.00001). — [GitHub blog](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)
- [vendor blog, self-measured] Bugbot resolution rate 52% (July 2025) to 78.13% (April 2026), LLM-judged on public repositories. — [Cursor blog](https://cursor.com/blog/bugbot-learning)
- [study, proposal only] A March 2026 arXiv paper on terminal coding agents proposes context-aware system reminders injected as a short user-role message just before each LLM call, with a capped nudge. I saw only the search summary, which reported no effect size. — [arXiv:2603.05344](https://arxiv.org/pdf/2603.05344)

### Inferences
- The studies agree on mechanism even where they differ on outcome: agents obey instruction files (tool mentions change behaviour by orders of magnitude), so the cost of a bad or redundant line is real. A self-improving harness that appends learnings is spending from a budget where every line changes behaviour and adds roughly proportional cost.
- The ETH result and SkillsBench point the same way on authorship: content written by the model about a repository or task, without external evidence, does not help on average (-0.5 to -2 points for generated context files; about -1.3 for self-generated skills), while human-curated content gives a small-to-large gain. Automatically generated learnings should therefore be treated as candidates needing evidence, not as rules.
- The McMillan study's null on file size and position is narrower than it may look: one trivial annotation rule, two TypeScript codebases, Claude models only. It does not contradict IFScale (many competing instructions) or Anthropic's "longer files reduce adherence" statement, but it does suggest that within-session decay matters more than where a rule sits in the file. That is the best available argument for re-asserting a rule at the point of action (a hook message) over polishing the file's layout.
- The two positive vendor results both involve learnings that are checked against ground truth before use (Copilot citations) or against outcomes after use (Bugbot signals). No positive measured result exists for unverified free-text memories.
- The Agent READMEs finding that files grow by small additions and almost never shrink is direct empirical support for expecting bloat by default in any append-driven learning loop.

### Gaps
- Re-injecting rules on every prompt: I found a design proposal (arXiv:2603.05344) but no study measuring whether per-prompt re-injection restores compliance, nor its cost. Blog claims (for example that compaction keeps about half of rules, or a 39% multi-turn drop attributed to Laban et al. 2025) were not traced to primary sources and are excluded as unverified.
- The ETH study covers Python only and measures task resolution, not convention adherence, security or review burden, which are the outcomes most rules target.
- No independent replication of the Copilot or Bugbot numbers; both are vendor self-reports, and Bugbot's uses an LLM judge.
- I did not read the full text of arXiv:2605.10039 (abstract only), so absolute compliance rates are not reported here.
- No study found that measures a full learn-from-sessions loop end to end on an existing repository over time.

## 5. How do teams keep a growing harness from bloating?

### Takeaway
The documented controls are hard read limits, size targets, scoping so content loads only when relevant, read-time verification with expiry, scheduled curation passes, and recurring agent "gardening" that opens small fix PRs. Deletion is the weak point: the one large empirical study finds context files are almost never pruned, and most vendors leave removal to a human.

### Cited Findings

**Budgets and limits**
- [vendor doc] Claude Code: "target under 200 lines per CLAUDE.md file." `@` imports "don't reduce its context cost, because imported files load together". — [Claude Code docs](https://code.claude.com/docs/en/memory)
- [vendor doc] Auto memory hard limit: only "the first 200 lines of `MEMORY.md`, or the first 25KB, whichever comes first" load at session start. After a write, Claude Code measures the file; near the limit it reminds Claude "to shorten it: keep one line per entry, move detail into topic files, and merge or drop stale entries"; over the limit the write succeeds but returns an error telling Claude to rewrite the index. — [Claude Code docs](https://code.claude.com/docs/en/memory)
- [vendor doc] Cursor: "Keep rules under 500 lines"; split large rules into composable ones. — [Cursor docs](https://cursor.com/docs/context/rules)
- [vendor doc] Factory: 80,000 characters at initial load, 40,000 per tool call; "These are caps, not targets. Smaller files are usually better." — [Factory docs](https://docs.factory.com/guides/power-user/memory-management)
- [practitioner] HumanLayer: "general consensus is that < 300 lines is best, and shorter is even better"; its own root file is "less than sixty lines". — [HumanLayer](https://www.humanlayer.dev/blog/writing-a-good-claude-md)
- [vendor blog, via secondary summary] OpenAI's team keeps AGENTS.md to roughly 100 lines as a table of contents. — [AI-Wiki note on the OpenAI post](https://businessdatasolutions.github.io/ai-wiki/sources/2026-02-11-lopopolo-codex-harness-engineering)

**Progressive disclosure and scoping**
- [vendor doc] Path-scoped rules in `.claude/rules/` "load only when Claude works with matching files"; subdirectory CLAUDE.md files load on demand; memory topic files are not loaded at startup and are read on demand through the `MEMORY.md` index. — [Claude Code docs](https://code.claude.com/docs/en/memory)
- [vendor doc] Cursor's "Apply Intelligently" (description match) and "Apply to Specific Files" (globs) modes serve the same purpose. — [Cursor docs](https://cursor.com/docs/context/rules)
- [practitioner] HumanLayer's `agent_docs/` pattern: task-specific instructions in separate self-descriptively named files, listed with short descriptions in CLAUDE.md; and point to `file:line` references instead of copying snippets, because snippets go stale. — [HumanLayer](https://www.humanlayer.dev/blog/writing-a-good-claude-md)
- [vendor doc] Cursor gives the same advice: reference files instead of copying contents so rules do not go stale. — [Cursor docs](https://cursor.com/docs/context/rules)
- [vendor doc] Block-level HTML comments in CLAUDE.md are stripped before injection, so maintainer notes (for instance provenance of a rule) cost no context tokens. — [Claude Code docs](https://code.claude.com/docs/en/memory)

**Staleness, verification and expiry**
- [vendor doc] Copilot: citations checked against the current branch before use; internal upvote/downvote of memories; default 90-day expiry, configurable 7 to 180 days for repository facts. — [GitHub docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)
- [vendor blog] Copilot refreshes a memory's timestamp when it is verified and used, so used memories persist and unused ones age out; contradicted memories are replaced with corrected versions. — [GitHub blog](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)
- [vendor blog] Bugbot disables an active rule that "consistently generates negative signal". — [Cursor blog](https://cursor.com/blog/bugbot-learning)
- [vendor doc] Claude Code `/doctor prompt-audit` finds instructions for older models, references to files or commands that do not exist, and contradictions across files, and proposes edits. — [Claude Code docs](https://code.claude.com/docs/en/memory)
- [vendor doc] Claude Code records a `modified` timestamp on memory files so age is visible on read. — [Claude Code docs](https://code.claude.com/docs/en/memory)

**Deduplication and curation**
- [vendor doc] Devin's weekly maintenance session merges same-topic entries, resolves contradictions by recency, flags entries with dead paths or deprecated APIs, and a monthly folder reorganisation tightens trigger descriptions; all changes need human approval, and the default is to keep and flag when unsure. — [Devin docs](https://docs.devin.ai/use-cases/gallery/scheduled-knowledge-maintenance.md)
- [vendor doc] Claude Code auto memory avoids duplication at capture time by skipping what the code or CLAUDE.md already says. — [Claude Code docs](https://code.claude.com/docs/en/memory)
- [vendor doc] Factory: "Duplicating rules across supported filenames spends context without adding signal"; "Do not use nested files to repeat root rules"; avoid "Stale directory inventories that drift from the repository." — [Factory docs](https://docs.factory.com/guides/power-user/memory-management)
- [vendor blog, via secondary summary] OpenAI: a recurring doc-gardening agent opens fix-up PRs for stale docs, and background tasks open small refactoring PRs against the golden principles; the motivation given is that a single large instruction file "rots instantly" and is "hard to verify". — [AI-Wiki note on the OpenAI post](https://businessdatasolutions.github.io/ai-wiki/sources/2026-02-11-lopopolo-codex-harness-engineering)

**Evidence that pruning does not happen by default**
- [study] Across 2,303 context files, "deletions are minimal" (median under 15 words) while additions are steady; the authors propose treating the files as configuration-as-code with CODEOWNERS review and linters that verify documented commands. — [arXiv:2511.12884](https://arxiv.org/html/2511.12884v1)
- [study] Removing redundant content is supported by the ETH result that generated files mostly duplicate existing documentation and add about 20% cost for no gain. — [arXiv:2602.11988](https://arxiv.org/html/2602.11988)
- [practitioner] Every's compound engineering guide gives no pruning or deprecation guidance for `docs/solutions/`. — [Every guide](https://every.to/guides/compound-engineering)
- [practitioner] Böckeler lists coherence of a growing harness as an unsolved problem. — [Böckeler](https://martinfowler.com/articles/harness-engineering.html)

### Inferences
- The anti-bloat techniques with the best support are the mechanical ones: a hard read limit that produces an error on overflow (Claude Code MEMORY.md), expiry unless re-verified (Copilot), and demotion on negative signal (Bugbot). Advice-only targets ("under 200 lines") coexist with the empirical finding that files only grow.
- For a rules registry with named enforcers, the Copilot pattern translates directly: each rule carries a citation (the enforcer, the file or symbol it concerns, the incident that created it) that can be checked mechanically, and a rule whose citation no longer resolves is stale by construction. Claude Code's prompt audit and Devin's maintenance prompt check the same thing (dead paths, missing commands) by inference instead.
- Promotion to a mechanical enforcer is itself a pruning move: once a lint or hook enforces a rule, the told version can shrink to a pointer or be removed, which is how the OpenAI team keeps AGENTS.md at about 100 lines while the rule count grows.
- Keeping provenance out of the context window (HTML comments in CLAUDE.md, frontmatter in separate files, an index with one line per entry) lets a harness keep the evidence needed for later pruning without paying for it on every prompt.

### Gaps
- No source reports measured results for any pruning policy (for example, compliance or cost before and after a cleanup), and no source gives an expiry period validated by experiment; Copilot's 90-day default is stated without justification.
- Token budgets expressed in tokens are rare; published limits are in lines, kilobytes or characters. I found no vendor guidance on a per-prompt budget for hook-injected reminders.
- Nothing found on detecting semantic duplicates between a told rule and an existing lint or test automatically, beyond LLM-judged audits.
- I could not verify from the primary source how OpenAI's doc-gardening and cleanup agents are scheduled or how many of their PRs are merged.
