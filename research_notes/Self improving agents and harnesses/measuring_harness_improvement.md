# Measuring whether a harness change improved a coding agent (state of knowledge, 2025 to November 2026)

Research date: 2026-11-18. Product formats cited here (Claude Code hook payloads, transcript JSONL, OpenTelemetry names, `claude plugin eval` schema) change between versions; every such fact below is tied to the page as fetched on 2026-11-18 and should be re-verified against the installed version before a toolkit relies on it.

Verification legend used in the findings:
- **[read]** = I fetched the primary page and the fact comes from it.
- **[snippet]** = the fact comes from a search-result summary of the linked page; I did not open the full text. Treat as a lead to confirm.

## 1. What signals can be collected locally from real agent sessions without a hosted service?

### Takeaway
Claude Code exposes four local signal channels that need no hosted service: hook payloads on stdin (33 documented events, all carrying `session_id`, `transcript_path`, `cwd`), the per-session JSONL transcript on disk, OpenTelemetry metrics and events (a `console` exporter and a localhost Prometheus endpoint exist; no general file exporter is documented), and git/CI state. Only the hook payloads and OpenTelemetry names are officially documented; the transcript JSONL schema is reverse-engineered by the community and its line types drift between versions, and the transcript is written asynchronously so it can lag the turn a hook is observing.

### Cited Findings

**Hooks (official, undated page; newest version mentioned on the page is v2.1.314)**
- [read] The hooks reference lists 33 events: `SessionStart`, `Setup`, `UserPromptSubmit`, `UserPromptExpansion`, `PreToolUse`, `PermissionRequest`, `PermissionDenied`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`, `Notification`, `MessageDisplay`, `SubagentStart`, `SubagentStop`, `TaskCreated`, `TaskCompleted`, `Stop`, `StopFailure`, `TeammateIdle`, `InstructionsLoaded`, `ConfigChange`, `CwdChanged`, `DirectoryAdded`, `FileChanged`, `WorktreeCreate`, `WorktreeRemove`, `PreCompact`, `PostCompact`, `PreModelSwitch`, `PostModelSwitch`, `Elicitation`, `ElicitationResult`, `SessionEnd`. — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks) (fetched 2026-11-18; only the first ~100k of ~294k characters was read, so per-event schemas late in the page were not verified)
- [read] Common input fields on every command hook (stdin JSON): `session_id`, `prompt_id` (UUID of the user prompt, matches the OpenTelemetry `prompt.id` attribute, absent before first input), `transcript_path`, `cwd`, `scratchpad_dir` (v2.1.257+), `permission_mode` (`default`, `plan`, `acceptEdits`, `auto`, `dontAsk`, `bypassPermissions`), `effort.level`, `hook_event_name`, and `agent_id` / `agent_type` when fired inside a subagent. — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks)
- [read] Tool events (`PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionRequest`, `PermissionDenied`) carry `tool_name`, `tool_input`, `tool_use_id`. `Stop` and `SubagentStop` carry `last_assistant_message`. `SessionStart` carries `source` (for example `resume`, `fork`) and sometimes `model`. `PreModelSwitch` / `PostModelSwitch` carry `from_model`, `to_model`. — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks)
- [read] Pitfall, stated by the docs: the transcript file is written asynchronously and may lag the in-memory conversation, so it may not contain the current turn's latest messages when a hook fires; the docs direct hook authors to `last_assistant_message` on `Stop` / `SubagentStop` for the current turn's final text. — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks)
- [read] Exit-code semantics matter for any guard used as a measurement point: exit 0 = success, exit 2 = blocking error (stderr becomes the reason; on `PostToolUse` it only shows stderr to the model, it does not undo), any other code = non-blocking error unless `"onFailure": "block"` is set (v2.1.295+). The page warns exit 1 is non-blocking. — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks)
- [read] `InstructionsLoaded`, `PreCompact`, `PostCompact` and `ConfigChange` exist as events, which is what makes "which rules were in context, and when did compaction happen" locally observable. (Payload fields for these were in the unread part of the page.) — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks)

**OpenTelemetry (official, undated page)**
- [read] Enable with `CLAUDE_CODE_ENABLE_TELEMETRY=1`; exporters are `OTEL_METRICS_EXPORTER` = `otlp` | `prometheus` | `console` | `none` and `OTEL_LOGS_EXPORTER` = `otlp` | `console` | `none`. The `console` exporter prints locally with no hosted service; `prometheus` serves `http://localhost:9464/metrics` (a scraper is still needed). No general file exporter is documented; `OTEL_LOG_RAW_API_BODIES=file:<dir>` writes API bodies to disk and `--debug-file` writes the debug log. — [Claude Code monitoring docs](https://code.claude.com/docs/en/monitoring-usage) (fetched 2026-11-18; first ~100k of ~176k characters read)
- [read] Metrics: `claude_code.session.count` (attr `start_type`), `claude_code.lines_of_code.count` (`type` added/removed), `claude_code.pull_request.count`, `claude_code.commit.count`, `claude_code.cost.usage` (USD), `claude_code.token.usage` (`type` input/output/cacheRead/cacheCreation), `claude_code.code_edit_tool.decision` (`tool_name`, `decision`, `source`, `language`), `claude_code.active_time.total` (`type` user/cli). Cost and token counters also carry `model`, `query_source`, `effort`, `agent.name`, `skill.name`, `plugin.name`, `mcp_server.name`. — [Claude Code monitoring docs](https://code.claude.com/docs/en/monitoring-usage)
- [read] Events: `claude_code.user_prompt` (`prompt_length`; prompt text redacted unless `OTEL_LOG_USER_PROMPTS=1`), `claude_code.tool_result` (`tool_name`, `tool_use_id`, `success`, `duration_ms`, `error_type`, `decision_source`, sizes; `tool_parameters` incl. `bash_command`, `git_commit_id`, `skill_name`, `subagent_type` only with `OTEL_LOG_TOOL_DETAILS=1`), `claude_code.api_request` (`model`, `cost_usd`, `cost_usd_micros`, `duration_ms`, `input_tokens` excluding cache, `output_tokens`, `cache_read_tokens`, `cache_creation_tokens`, `request_id`, `query_source`, `skill.name`, `plugin.name`), `claude_code.api_error`, `claude_code.api_refusal`, `claude_code.assistant_response`, and `claude_code.tool_decision` (`decision` accept/reject; `source` one of `config`, `hook`, `user_permanent`, `user_temporary`, `user_abort`, `user_reject`; `permission_mode`). — [Claude Code monitoring docs](https://code.claude.com/docs/en/monitoring-usage)
- [read] `tool_result` is not emitted for rejected calls; rejections appear only in `tool_decision`. — [Claude Code monitoring docs](https://code.claude.com/docs/en/monitoring-usage)
- [read] Cost caveat: `cost_usd` and `claude_code.cost.usage` are an estimate, not a billing figure; the docs direct users to billing data for authoritative spend. — [Claude Code monitoring docs](https://code.claude.com/docs/en/monitoring-usage)
- [read] Events (not metrics) carry `prompt.id`, `event.sequence`, `agent_id`, `parent_agent_id`, which allows per-prompt joins with hook payloads through `prompt_id`. — [Claude Code monitoring docs](https://code.claude.com/docs/en/monitoring-usage)
- [read] Tracing is beta (`CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1`, `OTEL_TRACES_EXPORTER` = `console` | `otlp` | `none`) with spans `claude_code.interaction` > `claude_code.llm_request`, `claude_code.tool` > `claude_code.tool.blocked_on_user` / `claude_code.tool.execution`; `claude_code.hook` spans need a detailed beta mode the page warns against in production and that needs organization allowlisting for interactive sessions. — [Claude Code monitoring docs](https://code.claude.com/docs/en/monitoring-usage)

**Transcripts (community-documented, not an official schema)**
- [read] A community reference describes each session as an append-only JSONL file at `~/.claude/projects/<encoded-project-path>/<session-id>.jsonl`, one JSON object per line, with top-level `type`, `uuid`, `parentUuid`, `timestamp` (ISO 8601), `sessionId`, `cwd`, `gitBranch`, `version`. `user` lines hold `message.content` as a string or content-block array (tool results arrive here as `tool_result` blocks keyed by `tool_use_id`); `assistant` lines hold `text`, `thinking`, `tool_use` blocks and `message.usage` with `input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`. — [claude-dev.tools JSONL format page](https://claude-dev.tools/docs/jsonl-format) (undated; fetched 2026-11-18)
- [read] The same page states that "the exact `type` values evolve with Claude Code versions" and declines to give a definitive list of system/meta line types (compaction boundaries, summaries, hook output, file snapshots, subagent coordination). — [claude-dev.tools JSONL format page](https://claude-dev.tools/docs/jsonl-format)
- [snippet] Community notes report that subagent transcripts are stored in separate files named `agent-<agentId>.jsonl` in a directory beside the main session, and that older versions instead inlined sidechain lines with `isSidechain: true` in the main file. — [oh-my-opencode Claude session stores reference](https://cdn.jsdelivr.net/npm/oh-my-opencode@4.18.2/dist/skills/coding-agent-sessions/references/claude.md); [Aditya Bawankule, "Claude Code Session Files: JSONL Format (2026)"](https://www.adityabawankule.io/blog/claude-code-session-jsonl-format)
- [read] `claude plugin eval` accepts a saved `.jsonl` transcript as `context.history_file` to resume a recorded conversation, and its `trace` grader target is "the session as JSON, one message per line" — the only official statements found that the transcript is replayable line-oriented JSON. — [Claude Code plugin evals docs](https://code.claude.com/docs/en/plugin-evals.md) (fetched 2026-11-18; requires v2.1.269+)

**Git history and pull-request outcomes**
- [read] Cursor's production quality signal is "Keep Rate": for a set of agent-proposed changes, "what fraction of those remain in the user's codebase after fixed intervals of time"; low keep rate is read as users having to fix or iterate. — [Cursor, "Continually improving our agent harness", 30 Apr 2026](https://cursor.com/blog/continually-improving-agent-harness)
- [snippet] A study of 8,106 fix-related agentic PRs (AIDev-pop) found 65.0% merged, ranging from 81.6% (Codex) to about 42–43% (Copilot, Devin), and explicitly states that whether high merge rates correlate with post-merge quality such as revert rates or defect introduction "remains unexamined". — [arXiv 2602.00164 (Feb 2026)](https://www.emergentmind.com/papers/2602.00164)
- [snippet] A task-level study on AIDev-pop (data to 1 Aug 2025) reports acceptance rates of 0.45 (Copilot), 0.67 (Cursor), 0.66 (Claude), and excluded revert-type PRs because only 16 existed across all agents. — [arXiv 2602.02345 (Feb 2026)](https://arxiv.org/html/2602.02345)
- [snippet] An analysis of 11,048 closed agentic PRs (9,799 human-reviewed) argues the "rejected" label is a poor proxy for agent failure. — [arXiv 2605.22534 (May 2026)](https://arxiv.org/html/2605.22534)

**Human corrections and interruptions**
- [read] Cursor uses an LLM to read the user's next message after agent output: moving to the next feature is treated as success, and pasting a stack trace is called "a reliable signal that it didn't" work. — [Cursor, 30 Apr 2026](https://cursor.com/blog/continually-improving-agent-harness)
- [read] Locally, the documented interruption/rejection signal is the `tool_decision` event with `source` = `user_abort` or `user_reject`, plus the `PermissionDenied` hook event. — [Claude Code monitoring docs](https://code.claude.com/docs/en/monitoring-usage); [Claude Code hooks reference](https://code.claude.com/docs/en/hooks)

**Tool-error signals**
- [read] Cursor classifies tool errors (`InvalidArguments`, `UnexpectedEnvironment` = model mistakes/context contradictions; `ProviderError`; `UserAborted`; `Timeout`), treats unknown errors as harness bugs, alerts when a tool's unknown-error rate passes a fixed threshold, and keeps per-tool, per-model baselines because "different models may mess up tool calls at different rates". — [Cursor, 30 Apr 2026](https://cursor.com/blog/continually-improving-agent-harness)

### Inferences
- A zero-dependency local toolkit has two officially documented capture points that need no network: (a) hooks writing their own append-only log from stdin payloads, and (b) the `console` OpenTelemetry exporter. Hooks are the sturdier of the two because the payload contract is documented and versioned per field, whereas console OTel output must be scraped from process output. Parsing `~/.claude/projects/**/*.jsonl` directly is the richest source but rests on an undocumented schema, so a "reports only what it checked" tool should record the `version` field per line and refuse (or mark unknown) line types it does not recognise rather than silently skipping them.
- Because the transcript lags asynchronously, a `Stop`-hook that reads `transcript_path` to grade the turn can miss the final messages; the hook payload itself (`last_assistant_message`, `tool_input`) is the reliable in-turn source, and transcript analysis is safer after `SessionEnd`.
- Git-derived signals (survival of agent-written lines after N days, fix-up commits touching the same hunks, reverts) are the local analogue of Cursor's Keep Rate, but they need a reliable agent-authorship marker (commit trailer, or `git_commit_id` from `tool_result` with `OTEL_LOG_TOOL_DETAILS=1`). Without one, churn cannot be attributed to the agent.
- Merge/acceptance is a weak outcome label on its own: published studies report it widely but also say rejection is a poor proxy for failure and that post-merge quality is unstudied.
- Token and cost fields in transcripts and OTel are estimates of list-price cost; they are good for relative with/without comparison within one model and version, not for absolute spend.

### Gaps
- No official Anthropic schema for the session JSONL was found. Fields such as `isSidechain`, `isMeta`, `toolUseResult`, compaction/summary line types, interruption markers, and whether `usage` is duplicated across multiple lines of one streamed assistant message could not be confirmed from any source I opened. These must be checked against real local files.
- The event-specific payloads for `InstructionsLoaded`, `PreCompact`/`PostCompact`, `UserPromptSubmit`, `PostToolUseFailure`, `StopFailure` and `SessionEnd` were in the unread portion of the hooks page and are not verified here.
- I found no published study measuring revert rate, fix-up-commit rate or line churn after agent commits; one paper names this as an open gap. GitClear-style churn reports were not retrieved.
- No source was found on using CI results as an agent-quality signal beyond "tests pass"; pitfalls such as flaky tests are covered only indirectly (infrastructure noise, section 3).

## 2. What metrics are used for agent quality inside a repository, and which are robust versus easily gamed?

### Takeaway
The consensus is to grade the outcome (final repository state, tests) rather than the path or the agent's own claim, to report reliability across repeated trials (pass@k and pass^k) rather than a single pass, and to treat efficiency numbers (tokens, turns, tool calls, latency) as "directionally useful" side metrics that do not show whether the job was done well. Metrics the agent or the harness can satisfy by construction (a "skill fired" check, a merged PR, a self-reported success) are the ones flagged as inflating or misleading.

### Cited Findings
- [read] Anthropic defines the vocabulary: task, trial (one attempt; multiple trials because "model outputs vary between runs"), grader, transcript, outcome (final environment state, "not what the agent claims"), evaluation harness, agent harness/scaffold; evaluating "an agent" means evaluating harness and model together. — [Anthropic, "Demystifying evals for AI agents", 9 Jan 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [read] Grader trade-offs: code-based graders (tests, string match, static analysis, tool-call checks) are fast, cheap, reproducible but brittle to valid variation; model-based graders are flexible but non-deterministic, costlier and need calibration against humans; human grading is the gold standard used mainly to calibrate. — [Anthropic, 9 Jan 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [read] "It's often better to grade what the agent produced, not the path it took"; for coding agents grade the outcome first (does it run, do tests pass), then add transcript grading. — [Anthropic, 9 Jan 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [read] pass@k = probability of at least one success in k trials; pass^k = probability all k succeed; a 75% per-trial rate gives about 42% pass^3. — [Anthropic, 9 Jan 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [read] Capability evals should start at a low pass rate; regression evals should sit near 100%; saturated evals stop showing improvement. A 0% pass rate is "most often a signal of a broken task". — [Anthropic, 9 Jan 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [read] Grader bugs dominate some results: Opus 4.5 scored 42% on CORE-Bench until grading and scaffolding fixes raised it to 95%. Balanced problem sets (cases where a behaviour should and should not occur) are needed to avoid one-sided optimisation. — [Anthropic, 9 Jan 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [read] Isolation failure as a gaming route: Anthropic reports Claude used git history from earlier trials to gain an unfair advantage when trials shared state. — [Anthropic, 9 Jan 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [read] Cursor says latency, token efficiency, tool-call count and cache hit rate are "directionally useful" but do not show whether the agent did a good job; its quality metrics are Keep Rate and LLM-judged satisfaction from the user's follow-up. — [Cursor, 30 Apr 2026](https://cursor.com/blog/continually-improving-agent-harness)
- [read] `claude plugin eval` excludes "the skill was invoked" graders from scoring in a with/without comparison because such a check "can never pass without the plugin, so counting it would push the without-arm toward zero and inflate Δ"; they are reported as indicators only. — [Claude Code plugin evals docs](https://code.claude.com/docs/en/plugin-evals.md)
- [read] Same docs: "If a case scores 1.0 both with and without the plugin, the plugin isn't what made it pass." — [Claude Code plugin evals docs](https://code.claude.com/docs/en/plugin-evals.md)
- [read] Cost as a first-class metric: context files raised inference cost by over 20% on average while not improving success. — [Gloaguen et al., arXiv 2602.11988, v1 12 Feb 2026, v3 29 Sep 2026](https://arxiv.org/abs/2602.11988)
- [snippet] The same study reports LLM-generated context files added about 3.92 steps per task (23% cost) on its own benchmark and 2.45 steps (20%) on SWE-bench Lite; agents did follow the files (more testing, more file traversal) without resolving more issues. — [arXiv 2602.11988 HTML](https://arxiv.org/html/2602.11988)
- [read] Reliability-over-duration metrics have been proposed: Reliability Decay Curve, Variance Amplification Factor, Graceful Degradation Score, Meltdown Onset Point; across 10 models and 23,392 episodes on 396 tasks, software-engineering graceful-degradation score fell from 0.90 to 0.44 from short to long tasks, frontier meltdown rates reached 19%, and memory scaffolds hurt long-horizon performance across all 10 models. — [Khanal, Tao, Zhou, "Beyond pass@1", arXiv 2603.29231, 31 Mar 2026](https://arxiv.org/abs/2603.29231) (abstract only)
- [snippet] "On Randomness in Agentic Evals" recommends reporting pass@1 estimated from multiple runs per task plus pass@k and pass^k. — [arXiv 2602.07150, Feb 2026](https://www.arxiv.org/pdf/2602.07150)

### Inferences
- Robust (hard to satisfy without doing the work): hidden or pre-existing tests passing on the final tree; fail-before/pass-after tests; survival of agent lines after a fixed interval; pass^k over repeated trials; with-minus-without delta on identical tasks.
- Easily gamed or confounded: self-reported completion; "skill/rule fired" counts (satisfied by construction); merge rate (reviewer behaviour, PR size, task mix); test pass rate when the agent may edit or delete tests; tokens or turns per task when used alone (a harness can lower them by doing less); rule-violation rate measured by a regex the agent can route around; any metric computed on tasks whose graders the agent can read.
- "Rule compliance followed, task success unchanged, cost up 20%" is a documented outcome (AGENTS.md study). A gate for a self-improvement loop therefore needs at least a pair: an outcome metric and a cost metric, with compliance as a diagnostic, not the objective.
- Repeated-mistake rate, time to green and human-intervention rate appear in practitioner framing (Cursor's follow-up classification is the closest published operationalisation) but I found no source that defines or validates them quantitatively.

### Gaps
- No source found that defines or validates "repeated-mistake rate", "time to green" or "human intervention rate" as agent-quality metrics with numbers.
- No published Keep Rate intervals, thresholds or baseline values (Cursor gives none).
- I did not retrieve METR, HAL/"AI Agents That Matter", or DORA-style sources; cost-controlled leaderboard methodology is therefore not covered here.

## 3. How are harness changes evaluated offline, at what cost, and with what statistical pitfalls?

### Takeaway
The standard offline design is a paired with/without comparison on the same tasks with several trials per task, outcome-graded; `claude plugin eval` (Claude Code v2.1.269+) implements exactly this for plugins, defaulting to 3 runs per arm, and repository-specific task sets are built from merged pull requests with fail-before/pass-after tests. The dominant pitfall is noise: on SWE-bench Verified a single run moves 2.2 to 6.0 points by chance and infrastructure alone moves Terminal-Bench 2.0 by up to 6 points, so small suites with a handful of runs can only detect large effects.

### Cited Findings

**`claude plugin eval` (official; hosted model calls required, runs locally)**
- [read] Requires Claude Code v2.1.269+, git 2.31+ if git is present, and a plugin directory. "Every eval run and every judge grader is a real model call on your account". — [Claude Code plugin evals docs](https://code.claude.com/docs/en/plugin-evals.md) (fetched 2026-11-18)
- [read] "One run of a non-deterministic agent tells you little, so each case runs three times by default." A run's score is the (weighted) fraction of graders passed; the case score is the mean across runs; a case passes at `--threshold` (default 1.0). `runs` may be 1 to 50. — [Claude Code plugin evals docs](https://code.claude.com/docs/en/plugin-evals.md)
- [read] Cost model: roughly cases × runs agent runs with the plugin, the same again for the no-plugin baseline, plus three short judge calls per `llm` or `baseline` grader per run. The docs' own one-case, six-run example shows `$0.41` and 74 s; the CI example sets `--max-cost-usd 20`. Reported cost is a list-price estimate. — [Claude Code plugin evals docs](https://code.claude.com/docs/en/plugin-evals.md)
- [read] Baseline: each case is repeated with no plugin; output shows `WITH`, `W/OUT`, `Δ`. `--ablation none` halves cost; `--ablation with-without` forces the comparison. The delta "is reported but never changes the exit code" — only the with-arm threshold gates CI (exit 0 pass, 1 below threshold or load/API failure, 2 partial on cost ceiling or auth, 130 interrupted, 143 terminated). — [Claude Code plugin evals docs](https://code.claude.com/docs/en/plugin-evals.md)
- [read] Six grader types: `regex`, `tool_used`, `tool_order`, `file_exists` (computed from transcript/files, free) and `llm`, `baseline` (judge model; `llm` passes on at least two of three votes). "There are no custom-code graders." An `llm` judge on `trace` sees only the first 12 and last 12 messages. `file_exists` and `files` count only files created during the run, not files modified. — [Claude Code plugin evals docs](https://code.claude.com/docs/en/plugin-evals.md)
- [read] Judge-noise guidance: an `llm` grader's answer "can differ between runs, and it differs more the longer the text it has to read"; use `regex` for long output; if the skill fired but Δ is negative "suspect the judge before the plugin". "A single run is noisy, so confirm any change at the default three runs before you trust it." — [Claude Code plugin evals docs](https://code.claude.com/docs/en/plugin-evals.md)
- [read] Isolation: each run is a `claude -p` child with a temporary home, working directory and configuration and only the plugin loaded. "Nothing personal or project-level loads": no user settings, hooks, `CLAUDE.md`, MCP servers, other plugins, memory or skills; no `.claude/`, `CLAUDE.md` or `.mcp.json` is read even if a scaffold script writes one. Case definitions are hidden from the agent. — [Claude Code plugin evals docs](https://code.claude.com/docs/en/plugin-evals.md)
- [read] Platform limit: granting `Bash` requires the OS sandbox; "Native Windows has no backend, so run shell-granting suites under WSL2"; without a backend each run is refused and usually scores 0. — [Claude Code plugin evals docs](https://code.claude.com/docs/en/plugin-evals.md)
- [read] Network/publishing: when signed in with a claude.ai subscription the HTML report is also published as a private artifact unless `--no-publish` is passed; `report.html` itself is self-contained and makes no external requests. Results are written to `evals/results/<timestamp>/aggregate-result.json` (`schemaVersion: 1`, camelCase, fields added without renames) with `partial`, `aggregates.overallScore`, `aggregates.meanDelta`, `cases[].aggregates.delta`, `costUsd`, `durationSeconds`, `claudeVersion`. — [Claude Code plugin evals docs](https://code.claude.com/docs/en/plugin-evals.md)
- [read] CI advice: pin `--model` and `--judge-model` "so a model rollout isn't mistaken for a plugin regression"; leave `partial: true` documents and runs with `skippedPaidGraders` out of trends. Scores from plugins with third-party hooks or real MCP servers are "advisory" unless run in an isolated environment, because hooks run outside the sandbox "and could modify the files the graders read". — [Claude Code plugin evals docs](https://code.claude.com/docs/en/plugin-evals.md)
- [read] The skill-creator plugin "runs a similar comparison with its own `evals/evals.json` format, and neither tool reads the other's case files". — [Claude Code plugin evals docs](https://code.claude.com/docs/en/plugin-evals.md)

**Building an evaluation set**
- [read] "20-50 simple tasks drawn from real failures is a great start"; early changes have large effects so small samples work; source tasks from manual checks, bug trackers and support queues; two domain experts should reach the same verdict; write a reference solution per task. — [Anthropic, 9 Jan 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [read] LLM-judge practice: give the judge an "Unknown" escape option, grade each dimension with a separate judge, calibrate against human experts. — [Anthropic, 9 Jan 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [read] Frameworks named by Anthropic: Harbor (containerised agent environments, registry including Terminal-Bench 2.0), Braintrust (offline evals plus production observability, `autoevals`), LangSmith (tracing, offline and online evals, datasets), Langfuse (self-hosted open source), Arize Phoenix (open source) / AX (SaaS). promptfoo is not mentioned in that article. — [Anthropic, 9 Jan 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [snippet] Repository-specific benchmarks from a repo's own merged PRs: RepoAgentBench (open source, "turns your merged PRs into reproducible coding-agent benchmarks") and Vals-Smith (Vals AI; hidden tests must fail before the original change and pass after the merged fix; waitlist access, i.e. hosted). — [repoagentbench on PyPI](https://pypi.org/project/repoagentbench/); [RuntimeWire on Vals-Smith](https://runtimewire.com/article/vals-smith-turns-merged-pull-requests-into-private-coding-agent-benchmarks)
- [snippet] A time-consistent design snapshots the repository at T0, derives the harness artefact (repository knowledge) from that snapshot, then evaluates on tasks from PRs merged after T0, running the same agent with and without the artefact. — [arXiv 2603.26137 (Mar 2026)](https://arxiv.org/html/2603.26137)
- [snippet] SWE-smith is a synthetic task generator whose authors say it does not produce hidden tests, "a crucial difference that makes SWE-bench more suitable for evaluation". — [SWE-smith, arXiv 2504.21798 (Apr 2025)](https://arxiv.org/pdf/2504.21798)
- [snippet] SWE-Bench++ harvests live PRs (bug fixes and features, 11 languages) and supports filtering by PR creation date for temporally separated evaluation sets. — [arXiv 2512.17419 (Dec 2025)](https://arxiv.org/html/2512.17419v1)
- [read] Cursor's CursorBench is an internal offline suite giving "a fast, standardized read on quality"; Cursor notes benchmarks only approximate real usage. — [Cursor, 30 Apr 2026](https://cursor.com/blog/continually-improving-agent-harness)
- [snippet] CursorBench tasks are sourced from "Cursor Blame", which traces committed code back to the agent request that produced it. — [Cursor, "CursorBench", 11 Mar 2026](https://cursor.com/blog/cursorbench)

**Statistics**
- [read] Anthropic's five recommendations: (1) report the standard error of the mean with every score, 95% CI = mean ± 1.96 × SEM; (2) cluster standard errors on the unit of randomisation — clustered errors "can be over three times as large as naive standard errors"; (3) reduce within-question variance by resampling and averaging per question; (4) analyse paired differences on the same questions — frontier models' per-question scores correlate 0.3 to 0.7, which shrinks the standard error of the difference; (5) use power analysis to choose the number of questions for a hypothesised effect size. — [Anthropic, "A statistical approach to model evaluations", 19 Nov 2024](https://www.anthropic.com/research/statistical-approach-to-model-evals); paper: [Evan Miller, "Adding Error Bars to Evals", arXiv 2411.00640, 1 Nov 2024](https://arxiv.org/abs/2411.00640)
- [snippet] "On Randomness in Agentic Evals" ran 60,000 SWE-bench Verified trajectories over three models and two scaffolds: single-run pass@1 varies by 2.2 to 6.0 points depending on which run is picked; standard deviation exceeds 1.5 points even at temperature 0; reported 2–3 point gains "may be noise"; recommends multiple runs per task and power analysis to set the run count. — [Bjarnason, Silva, Monperrus, arXiv 2602.07150, Feb 2026](https://www.arxiv.org/pdf/2602.07150)
- [read] Infrastructure noise: on Terminal-Bench 2.0 the gap between most- and least-resourced setups was 6 points (p < 0.01); infra error rate was 5.8% at strict 1x resource enforcement, 2.1% at 3x headroom (p < 0.001), 0.5% uncapped; on SWE-bench (227 problems × 10 samples) 5x RAM gave +1.54 points; naive binomial CIs are roughly 1–2 points and infrastructure effects "stack on top"; leaderboard differences below 3 points "deserve skepticism" until configuration is documented and matched; pass rates were anecdotally observed to vary by time of day; recommends running at multiple times and on multiple days. — [Anthropic, "Quantifying infrastructure noise in agentic coding evals", 5 Feb 2026](https://www.anthropic.com/engineering/infrastructure-noise)
- [snippet] Benchmark sizes for scale: the AGENTS.md study's own benchmark had 138 issues; Terminal-Bench 2.0 has 89 tasks; SkillsBench has 84 tasks and needed 7,308 trajectories for 7 agent-model configurations × 3 conditions. — [arXiv 2602.11988](https://arxiv.org/html/2602.11988); [Rick Hightower on LangChain's Terminal Bench work](https://rick-hightower.blogspot.com/2026/03/langchains-harness-engineering-from-top.html); [SkillsBench, arXiv 2602.12670](https://arxiv.org/html/2602.12670v1)

### Inferences
- How many runs: no source gives a single number, and the plugin-eval default of 3 runs per arm is a noise-reduction default, not a power calculation. My own textbook calculation (two-sided α = 0.05, power 0.80, independent two-proportion normal approximation, baseline pass rate 0.50) gives roughly 90 trials per arm to detect a 20-point lift, about 385 per arm for 10 points, and about 1,560 per arm for 5 points. Pairing on the same tasks with positive correlation, and averaging several trials per task, reduce these, but the order of magnitude explains why a 20–50 task suite at 3 runs can only gate on large effects (roughly 15–20 points or more), and why trials of the same task must be treated as a cluster rather than as independent samples.
- For a cheap automated gate, the affordable honest design is: a small fixed task set, the same tasks in both arms, n trials per task per arm, per-task paired difference, and a reported interval rather than a pass/fail on the raw mean. The gate should say "no detectable difference at this sample size" rather than "no regression".
- `claude plugin eval` cannot evaluate a repository's own `CLAUDE.md`, project hooks, project settings, memory entries or user-level skills, because none of those load inside a run. Only harness pieces packaged in the plugin under test (skills, agents, hooks, MCP servers) are exercised. A rule or memory entry must be wrapped as a plugin or evaluated by a separate headless with/without runner.
- On native Windows, plugin-eval suites that need `Bash` cannot run (no sandbox backend), so on this platform only read-only-tool cases or WSL2 runs are possible.
- A PR-replay evaluation set for a single repository has two contamination risks the sources point at: the agent reading the fix from git history (Anthropic's shared-state anecdote) and the harness artefact having been written after, and with knowledge of, the PR being replayed (the motivation for the T0 snapshot design). Checkout must be at the parent commit with later history removed, and rules under test must predate the task or be excluded.
- LLM-as-judge is unsuitable as the sole gate for a tool that "reports only what it checked": the official guidance itself treats judge verdicts as noisy, truncates the trace it shows the judge, and recommends deterministic graders for long outputs.

### Gaps
- The explicit power-analysis formula from arXiv 2411.00640 was not retrieved (abstract only); the sample sizes above are my own approximation, not the paper's.
- promptfoo, Inspect (beyond its `epochs` resampling parameter, mentioned in Anthropic's statistics post), Braintrust and LangSmith documentation were not opened; their costs, offline capability and coding-agent support are not verified here. Braintrust and LangSmith are hosted services by default per Anthropic's description; Langfuse and Phoenix are described as self-hostable.
- RepoAgentBench and Vals-Smith details (test-extraction method, cost per task, maturity) come from search summaries only.
- No source gave a per-task dollar cost for PR-replay evaluation of a coding agent; the only concrete figure found is the docs' illustrative `$0.41` for six short plugin-eval runs.
- Hamel Husain and Eugene Yan write-ups were not retrieved.

## 4. How are harness changes evaluated online, and what guards against regression to the mean and novelty effects?

### Takeaway
The one detailed public account is Cursor's: harness variants are deployed side by side and A/B tested on real usage, read through Keep Rate and LLM-judged follow-up satisfaction, with per-tool, per-model error baselines and anomaly alerts as guardrails. Effect sizes in production are small (fractions of a percent to a few percent), which is far below what a single developer's session volume can resolve; I found no source on interleaving, sequential testing, novelty effects or regression to the mean specifically for coding-agent harnesses.

### Cited Findings
- [read] "We deploy two or more harness variants side by side and A/B test them on real usage." Cursor shelved one change (a pricier summarisation model) because it made "a negligible difference in agent quality that wasn't worth the higher cost". — [Cursor, 30 Apr 2026](https://cursor.com/blog/continually-improving-agent-harness)
- [snippet] In Cursor's semantic-search A/B test (same model, one arm without semantic search) agent code retention rose by 0.3%; the post notes the effect is diluted because the test ran on all agent queries, not only those needing search. A secondary summary reports 2.6% on large codebases (not confirmed in the primary post). — [Cursor, "semsearch", 6 Nov 2025](https://cursor.com/blog/semsearch); secondary: [ZenML LLMOps database summary](https://www.zenml.io/llmops-database/enhancing-ai-coding-agent-performance-with-custom-semantic-search)
- [read] Guardrails rather than outcome metrics: alerts on unknown-error rate per tool, anomaly alerts when expected errors exceed a per-tool, per-model baseline, and a weekly automated log scan that files tickets; a focused sprint cut unexpected tool-call errors "by an order of magnitude". — [Cursor, 30 Apr 2026](https://cursor.com/blog/continually-improving-agent-harness)
- [read] Anthropic places A/B testing, production monitoring, user feedback, manual transcript review and automated evals in a "Swiss cheese" model: no single layer catches every issue. — [Anthropic, 9 Jan 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [read] Confounders that mimic a harness effect in before/after comparisons: a model rollout ("pin it in CI so a model rollout isn't mistaken for a plugin regression"), managed policy differences between machines, and the Claude Code version (recorded as `claudeVersion` in results). — [Claude Code plugin evals docs](https://code.claude.com/docs/en/plugin-evals.md)
- [read] Time-of-day variation in pass rates was observed anecdotally (attributed to API latency), which is a confounder for any before/after comparison run at different times. — [Anthropic, 5 Feb 2026](https://www.anthropic.com/engineering/infrastructure-noise)
- [read] Local attribution fields that make per-session arm assignment possible: `session.id`, `prompt.id`, `app.version`, `model`, `skill.name`, `plugin.name`, and custom keys via `OTEL_RESOURCE_ATTRIBUTES`. — [Claude Code monitoring docs](https://code.claude.com/docs/en/monitoring-usage)

### Inferences
- Regression to the mean is the specific hazard of a self-improvement loop: rules are proposed after a bad session, and the next sessions would look better on average even with no change. The only defence consistent with the sources is a concurrent control (randomise sessions or tasks to with/without at the same time, same model, same version) rather than a before/after comparison; where that is not possible, the report should label the comparison as uncontrolled.
- With Cursor-scale effects of 0.3% to a few percent in retention, online A/B on one repository's traffic is underpowered for anything but large effects or rare-but-catastrophic guard metrics (tool error spikes, rule-violation spikes). Online data in a local toolkit is therefore better used as a canary (did anything get clearly worse) than as proof of improvement.
- Because hooks receive `session_id` at `SessionStart`, a deterministic hash of the session id could assign an arm locally with no service; the assignment and the model/version must be logged with each outcome so mixed-version comparisons can be excluded. (Design inference; no source describes this for Claude Code.)
- A before/after comparison should, at minimum, hold constant or stratify by model, Claude Code version and task type, and should not span a model switch.

### Gaps
- No source found on interleaving, sequential testing (alpha spending, always-valid p-values) or novelty-effect controls applied to coding-agent harness rollouts. General experimentation literature exists but was not retrieved, so nothing is cited.
- No published numbers for Keep Rate baselines or the satisfaction classifier's accuracy.
- The April 2026 Cursor figures quoted by a secondary article (+2.28% persisted edits, −3.13% dissatisfied follow-ups) could not be verified against a primary Cursor post and are not relied on here.
- OpenAI and Sourcegraph engineering posts on online agent evaluation were not retrieved.

## 5. What is known about measuring instruction or rule compliance, compliance decay over a long session, and re-injection?

### Takeaway
Controlled evidence exists for two things: adherence falls as the number of simultaneous instructions grows (best models about 68% at 500 instructions, with a bias toward earlier instructions), and agents do follow repository context files, which changes behaviour and cost without necessarily improving outcomes. Evidence for compliance decay within a long coding session, and for the benefit of re-injecting rules, is anecdotal practitioner writing; I found no controlled study that measures re-injection.

### Cited Findings
- [read] IFScale: 500 keyword-inclusion instructions in a business-report task, 20 models from seven providers; the best frontier models reach about 68% accuracy at 500 instructions; accuracy degrades with instruction density in three distinct patterns related to model size and reasoning; models show a bias toward earlier instructions. — [Jaroslawicz et al., "How Many Instructions Can LLMs Follow at Once?", arXiv 2507.11538, 15 Jul 2025](https://arxiv.org/abs/2507.11538) (abstract only)
- [snippet] Agents respect context-file instructions: both LLM-generated and developer-written files "encourage broader exploration (e.g., more thorough testing and file traversal), and coding agents tend to respect their instructions", yet this did not translate into more resolved issues. — [Gloaguen et al., arXiv 2602.11988](https://arxiv.org/html/2602.11988)
- [read] Long-horizon degradation is measurable at the task level: software-engineering graceful-degradation score falls from 0.90 to 0.44 across duration buckets, and memory scaffolds hurt long-horizon performance across all 10 models tested. The abstract does not describe measuring constraint adherence or re-injection. — [arXiv 2603.29231, 31 Mar 2026](https://arxiv.org/abs/2603.29231)
- [snippet] Anecdotal: a developer write-up reports a formatting rule holding for tool calls 1–10, degrading at 11–15 and failing after roughly 15 calls. Not a controlled study. — [Grass, "Why Your Claude Agent Ignores Rules Past ~15 Tool Calls"](https://codeongrass.com/blog/why-claude-agent-ignores-rules-past-15-tool-calls/)
- [snippet] Anecdotal: practitioner articles describe rules that remain in context but stop being applied mid-session, and recommend restating constraints partway through a long task; none of the excerpts cites a measurement of the effect of restating. — [Unblocked, "What Is Context Rot?"](https://getunblocked.com/blog/what-is-context-rot/index.md); [LogRocket, context rot article](https://blog.logrocket.com/context-rot-slowing-down-your-ai-agent-how-fix/)
- [read] Cursor observed a model-specific behaviour change as context filled ("context anxiety", refusing work), reduced by prompt adjustments — evidence that context fill level changes behaviour, measured per model. — [Cursor, 30 Apr 2026](https://cursor.com/blog/continually-improving-agent-harness)
- [read] Mechanisms for measuring compliance deterministically exist in the plugin-eval grader set: `tool_used` with `min: 0, max: 0` (a tool or command was never called), `tool_order` (A before B), `regex` with `match: not_contains` over the trace or a file. — [Claude Code plugin evals docs](https://code.claude.com/docs/en/plugin-evals.md)
- [read] Hooks that can inject context: plain stdout on exit 0 is added as context on `UserPromptSubmit`, `UserPromptExpansion`, `SessionStart` and `PostModelSwitch`; `PreCompact`/`PostCompact` and `InstructionsLoaded` events mark when rules may have left or entered context. — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks)

### Inferences
- Rule compliance is most reliably measured for rules that have a mechanical signature in the tool-call stream or the diff (forbidden command, required ordering, forbidden file pattern, required trailer). For such rules the violation rate per session, and its position in the session (tool-call index, tokens consumed, before/after compaction), can be computed locally from hook logs with no judge. Rules without a mechanical signature need an LLM judge and inherit judge noise.
- Decay should be measured as a curve (violation probability against turn or tool-call index, and a separate before/after-compaction split), not as a single per-session rate, because a per-session rate confounds session length with decay.
- The IFScale result argues that every added rule has a cost to the others; a self-improvement loop that only ever adds rules will predictably lower adherence to each. The total instruction count in context is therefore a metric worth tracking alongside per-rule compliance.
- The re-injection hypothesis is testable locally with a paired design (same long task, with and without a `UserPromptSubmit` or `PostCompact` re-injection hook, compliance measured by deterministic graders), but until such a test is run its benefit is unproven; a toolkit should not present re-injection as an evidenced fix.
- Compliance and outcome must be reported separately: the AGENTS.md study is a case where compliance was high and outcome did not improve.

### Gaps
- No controlled study was found that measures instruction-compliance decay as a function of turn count or context fill in coding-agent sessions.
- No controlled study was found that measures the effect of re-injecting rules (periodically, per prompt, or after compaction). This is the largest evidence gap in the assignment.
- IFScale tests keyword inclusion in a single generation, not multi-turn agent rules; transfer to coding sessions is unverified. Full-paper decay curves and the size of the primacy effect were not retrieved.
- The payload of `InstructionsLoaded` (which files, which trigger) was not verified.
- A practitioner claim that Claude Sonnet shows "a linear decline in instruction adherence" with instruction count had no stated methodology and is not relied on.

## 6. Which published results show a harness change measured well, with numbers?

### Takeaway
Three results stand out for holding the model fixed and varying only the harness artefact: the AGENTS.md study (context files: no real success gain, more than 20% extra cost), SkillsBench (curated skills +16.2 points on average, self-generated skills no benefit, 16 of 84 tasks worse), and LangChain's self-reported Terminal-Bench 2.0 gain from 52.8% to 66.5% with gpt-5.2-codex fixed. Read against the noise results (2.2 to 6.0 points run-to-run, up to 6 points from infrastructure), only the larger of these deltas are clearly outside noise.

### Cited Findings
- [read] AGENTS.md study: authors Gloaguen, Mündler-Sasahara, Müller, Raychev, Vechev; v1 12 Feb 2026, v3 29 Sep 2026; two complementary settings; context files increase inference cost by over 20% on average. — [arXiv 2602.11988](https://arxiv.org/abs/2602.11988)
- [snippet] Same study: LLM-generated context files slightly lowered success (about 0.5–2% averaged across agents); developer-written files gave about a 4% gain on the authors' AGENTbench; agents tested were Claude Code (Sonnet 4.5), Codex (GPT-5.2, GPT-5.1 Mini) and Qwen Code; evaluation used SWE-bench Lite plus a 138-issue Python benchmark from repositories that already had developer-written context files. Commentary notes it is Python-only, issue-style, and does not break down which kinds of instruction help or hurt. — [arXiv 2602.11988 HTML](https://arxiv.org/html/2602.11988); commentary: [ArXivIQ summary](https://arxiviq.substack.com/p/evaluating-agentsmd-are-repository)
- [snippet] SkillsBench: 84 tasks, 11 domains, each run under no skills / curated skills / self-generated skills, 7 agent-model configurations, 7,308 trajectories. Curated skills raise pass rate by 16.2 points on average, from +4.5 (software engineering) to +51.9 (healthcare); 16 of 84 tasks show negative deltas; self-generated skills average about −1.3 points versus no skills. One listing gives a conflicting +12.66 figure for curated skills; the arXiv paper's 16.2 is the figure to prefer. — [SkillsBench, arXiv 2602.12670, Feb 2026](https://arxiv.org/html/2602.12670v1)
- [snippet] LangChain: deepagents-cli went from 52.8% to 66.5% on Terminal Bench 2.0 (+13.7 points) changing only the harness, model fixed at gpt-5.2-codex; levers named were system prompt, tools, middleware, self-verification, tracing, time-budget warnings and reasoning-effort trade-offs (more reasoning can use over 2x tokens/time against task timeouts). Self-reported on a vendor blog; Terminal-Bench 2.0 has 89 tasks. — [LangChain, "Improving Deep Agents with harness engineering" (early 2026)](https://blog.langchain.com/improving-deep-agents-with-harness-engineering)
- [read] Anthropic: fixing grading and scaffolding moved Opus 4.5 on CORE-Bench from 42% to 95% — a harness-and-grader effect larger than any model gap. — [Anthropic, 9 Jan 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [read] Anthropic: resource configuration alone moved Terminal-Bench 2.0 by 6 points (p < 0.01) and SWE-bench by 1.54 points at 5x RAM (227 problems × 10 samples) — an example of a harness-environment variable measured with stated sample size and p-values. — [Anthropic, 5 Feb 2026](https://www.anthropic.com/engineering/infrastructure-noise)
- [snippet] Cursor's semantic-search test is a held-model ablation measured online: +0.3% code retention across all agent queries. — [Cursor, 6 Nov 2025](https://cursor.com/blog/semsearch)
- [snippet] Same-model scaffold spreads on SWE-bench Pro: Claude Opus 4.5 at 45.89% under Scale's standardised SWE-agent scaffold versus 51.80% under Auggie, with a separate listing of 55.4% for Claude Code. Reported by secondary sources. — [FutureAGI, "coding agent harness benchmark"](https://futureagi.com/blog/coding-agent-harness-benchmark/); [mpt.solutions, "The model doesn't matter, the harness does"](https://www.mpt.solutions/the-model-doesnt-matter-the-harness-does/)
- [snippet] Repeated-run confirmation of a harness method: an online-monitoring and corrective-steering method reports 36.58% to 46.56% on SWE-bench Verified for one model, holding across repeated runs. — [arXiv 2608.06701 (Aug 2026)](https://arxiv.org/pdf/2608.06701)
- [snippet] Negative harness result: memory scaffolds hurt long-horizon performance across all 10 models in a 23,392-episode study. — [arXiv 2603.29231](https://arxiv.org/abs/2603.29231)

### Inferences
- The well-measured results share four properties a local toolkit can copy: the model is pinned; the same tasks run in both arms; the cost delta is reported beside the success delta; and negative per-task deltas are reported (16 of 84 in SkillsBench) rather than only the mean.
- Two of the three headline results cut against automated self-improvement by default: LLM-generated context files slightly hurt, and self-generated skills gave no benefit, while human-curated artefacts helped. A loop that writes its own rules should expect a null or negative effect as the prior and require evidence to keep each rule.
- Published harness gains under about 3 to 6 points on these benchmarks cannot be distinguished from run-to-run and infrastructure noise unless multiple runs and intervals are reported; the LangChain (+13.7) and SkillsBench (+16.2) deltas are large enough to be credible in direction, though LangChain's is self-reported and its run count was not verified.
- Domain matters: curated skills helped software engineering least (+4.5 points) in SkillsBench, which suggests harness additions for coding tasks start from a smaller expected effect than in other domains.

### Gaps
- Several scaffold-only figures appear only in secondary sources and could not be verified against primary ones: Epoch AI's "up to 20 points" on SWE-bench Verified, Claude 3.7 moving from 62.3% to 70.2% with a custom scaffold, and Claude Sonnet 4.5 at 43.2% (SWE-agent) versus 59.8% (Cline). They are not relied on above.
- Two 2026 preprints surfaced as leads but were not opened: arXiv 2608.26218 (reported to hold model and tasks fixed and vary only the harness) and arXiv 2609.17394 ("Coding Agents Have Converged", reported within-model scaffold ranges up to 29.8 points, benchmark unclear).
- The LangChain post's run count, confidence intervals and exact publication date were not verified (search summary only).
- No controlled study was found for the effect of hooks, memory entries or sub-agent definitions specifically (as opposed to context files and skills) with the model held fixed.
- The AGENTS.md per-agent success tables and the v3 revisions (29 Sep 2026) were not read in full; the 0.5–2% and 4% figures come from search summaries of the paper.
