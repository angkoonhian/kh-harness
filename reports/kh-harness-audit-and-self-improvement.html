Audit findings and a plan for a harness that improves itself

The write path is disciplined and the tests pass. The weak point is narrower: wherever a check could not look, or a hook chose to stay quiet, the kit reports that everything is fine. That has to be fixed before a learning loop is built on top of it, because the loop would learn from those signals.

Three read-only audits (CLI core, generated hooks, skill and product) and five research threads. Findings marked "ran" were reproduced in throwaway repositories; the rest were reasoned from code or documentation and say so.

Your question

Can it improve the harness autonomously? Yes, inside a policy you set once.

The loop can run on its own for almost every step: watching sessions, spotting a repeated mistake, drafting a rule with an enforcer, testing it against recorded history, trialling it silently, and retiring it when it stops earning its place.

Two kinds of change should not happen without you: anything that can block work, and anything that puts text into the model's prompt. Those are where the documented failures happened. You can still make them automatic by writing a promotion policy, for example "promote after 5 silent firings with no false positives". The policy file is yours, and the loop cannot edit it.

So the design is slower than full autonomy, and it is still autonomous: you set the bar once, and the harness clears it or does not.

Audit

Three patterns explain most of the findings

"Could not look" becomes "nothing there"

An unreadable folder, a settings file with a BOM, a malformed manifest and a push URL are each treated as absent. The credential sweep then says verified.

Silence only ever grows

Hook counters never reset after a passing run. Each bound decays into "quiet for the rest of the session", and a missing or crashed linter looks the same as a clean file.

Safety is applied per call site

Containment exists, but detect's write skips it. Provenance checks protect files, but not settings patches. The skill describes gates the CLI cannot honour.

What already works and should be kept

  • Two-pass apply: the allowlist and containment check cover the whole batch before any write.
  • Layered removal gates: uninstall checks the allowlist, containment, a generator-producible path, the in-file stamp and the body, and re-derives at delete time.
  • Shared evidence modules: a check and its generator read the same derivation, so they cannot drift apart.
  • Redaction by omission: hook commands and script bodies never reach detect.json.
  • Honest documentation: the README discloses costs, litter and limits, including that its own eval measures nothing.
  • Tier 1 fixes hold: unborn HEAD, CRLF hashing and placeholder-then-literal were re-tested and pass.
Research

What the evidence says about self-improvement

Two research rounds. The second read the papers and source code in full and corrected the first.

The complete record of every run comes first. Meta-Harness's guide says "log everything in a navigable format", and every reference implementation keeps an archive of candidates with parent links and scores. The loop then has five more parts: an evaluator the agent cannot touch, a diagnosis step, a proposer, a selection rule, and a ledger of past changes with their measured effect.

Expect small gains. Against the authors' own minimal starting points, papers report 5 to 30 points. Independent re-runs on unseen tasks cut that to roughly 0 to 4, and nobody has measured a loop on one repository over months with a human reviewing.

How self-improvement fails

  • Judge tampering: the Darwin Gödel Machine removed its own hallucination markers and fabricated a passing test log. Humans found it by reading the lineage.
  • Bloat and collapse: a study of 2,303 context files found they grow by small additions and are almost never pruned.
  • Writable configuration as an attack target: several CVEs involve agents' own settings, rules and MCP files, including two in Claude Code project settings.
  • Guardrails routed around: only anecdotal reports exist of an agent weakening its own rules without injection.

Where the gap in existing tools is

claude-reflect, claude-mem, ECC's continuous learning and Claude Code's own memory all turn learnings into prose. The largest write without approval and cannot undo. No surveyed tool combines an inventory-first install, a write manifest and clean uninstall with learning that ends in a named enforcer. kh-harness already has the first three. This claim is bounded by a search of GitHub, vendor docs and a few web searches.

Proposal

The evidence ratchet: how the loop runs, and who decides each step

This is my proposed design, not something you have agreed. Each learning is one registry entry with one enforcer, a recorded reason, and its own manifest record so it can be removed alone.

automatic

Record every run

Hooks append every tool call, prompt, failure and enforcer firing to a local log. Each event carries the manifest hash, so the log knows exactly which harness produced it.

automatic

Find recurrences

Plain code, no model: the same tool and input failing the same way in two or more sessions under the same harness and model.

you, at first

Name the pattern

You label the first batches of recurrences. Those labels become the failure taxonomy the loop uses afterwards.

automatic

Draft one entry

The model reads the raw log and drafts one rule with one enforcer: a lint rule, then a test, then a hook, and prose only as a last resort.

automatic

Replay twice

The script runs the enforcer. It must fire on the recorded mistake and stay silent after the fix, then stay silent across the whole repository. Expect about half to fail here.

automatic

Silent trial

The enforcer runs in live sessions and only logs what it would have done. It cannot block and adds nothing to the prompt.

your policy, or your approval

Promote

It starts blocking or warning. Approval is tied to the exact content, so a later byte change voids it.

automatic

Ledger and measure

Every proposed, accepted, rejected and retired change is recorded with its evidence and measured effect. Reports count firings and what followed, at the sample size seen.

automatic

Demote or retire

A learned enforcer that keeps misfiring drops back to silent. One whose cited code is gone is retired. Every change is logged and reversible.

What the loop can never touch

  • The hooks, gate scripts, manifest, event log and promotion policy sit outside its write scope, and detect flags any byte change to them.
  • Rules you wrote and the kit's base enforcers are never demoted or retired by the loop.
  • Sessions that read untrusted content are marked, so text from a web page cannot become a "learning".
  • Rule text is escaped and stripped of invisible characters before it is shown for approval or injected.

What changes in the kit's doctrine

Today the non-goals say the kit never writes a rule. Under this design the scripts still never author one: the model drafts, the script validates, and promotion follows your approval or your policy. The non-goal needs rewording to say that plainly.

Order of work

First

Make every signal true

  • Give every reader three outcomes: absent, unreadable, ok. Unreadable blocks verified.
  • One credential pattern table shared by the sweep and the hook mask; stop skipping tracked files by folder name.
  • Reset hook suppression on a clean run, and give hooks a "did not verify" message distinct from success.
  • Replace the substring redaction that deletes diagnostics.
  • Provenance gates for settings patches; containment for detect's write.
  • Truthful summaries: typed proposals and an honest "nothing to write" line.
Alongside

The session log, so history starts accumulating now

  • Append-only files on your machine, written by hooks, outside tracked files and outside the loop's write scope.
  • Every event stamped with the manifest hash, Claude Code version and model.
  • Successes logged as well as failures; the agent's own "done" claims stored as claims, never as evidence.
  • A version-checked transcript reader for what hooks cannot see: interrupts, cancelled tools and most permission denials.
  • A recurrence report that is useful with no model and no loop.
  • Depends on the credential-mask fix above, because tool output contains secrets.
Second

Foundations the loop needs anyway

  • Ship the changes research keeps rediscovering as detected defaults: a submission guard and loop and budget warnings, beside the existing verify-before-finishing gate.
  • An upgrade path, so a fixed hook reaches repositories that already installed it.
  • detect --check with non-zero exits, for CI and teams.
  • Scoped apply, so the skill's phase gates are real, and an explicit CLI path in the skill.
  • A read-only health skill the model can invoke, which also makes the kit measurable.
  • An answers file, so declined proposals are not asked again.
Third

The evidence ratchet

  • The change ledger, before any proposer.
  • Your labelled failure taxonomy from the recurrence report.
  • A learn command: draft, replay twice, silent trial.
  • Promotion policy, content-bound approval, per-learning manifest records and single-learning revert.
  • Demotion, retirement and a registry budget.
Later, opt-in

Paired runs for large effects

Run the same tasks with and without a change to catch a clear regression. Useful for big differences only; one repository cannot resolve small ones, and the official eval tool needs WSL2 on Windows for suites that use the shell.

Decisions that are yours

  • How much the log captures: the research report recommends structure only by default (tool, status, error line, sizes, hashes), because full tool input and output copies secrets outside Claude Code's 30-day clean-up. You asked for as much as possible, and full content is what improvers read in the papers. I would capture full content once you enable the log on a machine, scrubbed at write time, with a retention limit you set.
  • Default autonomy: I would ship with promotion requiring approval, and the policy file as an opt-in. The alternative is a default policy that promotes automatically from day one.
  • What counts as a repeat: I would start at two occurrences, which matches practitioner guidance but has no measured basis.
  • Fixes before features: I recommend the order above. Starting the ratchet first would mean building it on hooks that currently go silent.
